# Module 2.7: Chapter 2 Individual Performance Assessment

**Quarter 1 · Week 8 · Wed Sep 30, 2026 · One meeting · Individual · ~53 minutes**

The individual half of the chapter's assessment, and the sibling of the Group PA two
days before it: same chapter, same week, same in-app shape, sat alone. Five lessons,
17 items, 100 points — the identical skeleton to 1.7, with one thing genuinely new.

## The one thing that is new: Part D is JavaScript

1.7's Part D was a chart and pseudocode, and the reason was stated plainly there —
Chapter 1 had not taught a conditional, so a test that asked for working code would
have been testing shCode rather than the course.

Chapter 2 has taught conditionals, three loop forms, `switch`, `break`/`continue` and
`try`/`catch`. **D2 is real, runnable JavaScript from here on**, on this test and on
every chapter test after it. That is the whole difference between the two papers; the
parts, the weights, the forms mechanism, the test mode and the no-retake rule are all
carried over unchanged.

| --- | --- | --- |
| D1 | chart, three shapes | chart, **hexagon legal** (§2.2) |
| D2 | pseudocode for the charted problem | **JavaScript**, including one nested loop |

**This spread is even, and that is a contrast worth recording rather than a
coincidence.** 1.7 ran 44 and 30 points into §1.2 and §1.5 — 74% of the paper in two
modules, with §1.4 at 8 — and the note there explained why: tracing only worked on
code Chapter 1 permitted you to run, and Part D was pure design. Neither constraint

The range here is 15 to 24. No module needed padding and none had to be skimped.

The blueprint's named requirements all land: `if`/`else if`/`else` (2.1 trace, D2),
the truthiness traps (2.1 trace and short answer), `for` vs `while` (2.2 short
answer), `switch` with correct `break` placement **and one fall-through question**
(2.3 trace and bug), `break`/`continue` (2.4 bug, D2), **one nested-loop trace in
Part B and one nested-loop write in Part D** (2.4), and a `try`/`catch` around code
that throws (2.5 trace and bug).

**Two of those items need pinning down before they are authored, or they will be
written wrong.**

**The 2.4 bug must be a `while`, and the word is "update", not "increment".** In a
`for` loop `continue` still runs the third clause, so "`continue` past the increment"
is not a bug there at all — it is only a bug when the update is a statement in the
body that `continue` jumps over, which is a `while`. The course's own lesson is
`2-4-16-reading-continue-while-trap`, titled for the loop form precisely because the
form is the bug. Authoring it as a `for` produces a snippet with nothing wrong in it.

**And that bug hands its own answer to the student, through the runner.** The correct
snippet never terminates. That is safe — `LessonWorkspace` runs student code in a
Worker with `RUN_TIMEOUT_MS = 3000` and kills it, built deliberately because "Module
2.4 teaches infinite loops" (`components/LessonWorkspace.tsx:340-344`) — so no tab
freezes. The problem is what it *prints*:

> Your code was still running after 3 seconds, so it was stopped. That usually means a
> loop never reaches its stopping point — **check that the value in the condition
> actually changes inside the loop.**

That is the repair, named. It is the same giveaway the 2026-09-02 narrowing stripped
out of Part C's checklist — which now names only the symptom — reappearing one layer
down, from the platform rather than the lesson, on the one Part C item that can
trigger it. Either this bug does not go in Part C, or the runner needs a summative
message that reports the stop without diagnosing it.

## The ceiling this test may not exceed

**No functions, no arrays, no objects.** Those are Chapter 3. Every snippet on this
paper is a top-level script. **Assumes:** Chapter 1 variables and types, and nothing
else.

**Iteration comes from the counter or from a string.** Same constraint the PA works
under — `word[i]` and `word.length` (`2-2-17a-example-walk-a-word`) are the only way
to walk data before §3.3. A Part B trace that iterates a list has silently imported
Chapter 3.

**Five shapes, and this is the first test where a fifth one is legal.** Oval,
rectangle, diamond, parallelogram — plus the **loop-setup hexagon**, released at §2.2
(Appendix D §D.2). 1.7 could not *require* the parallelogram because book exercise
1.5.11 asks for exactly three; that argument does not extend here, because the rule
Appendix D §D.2 actually states is about *release* — "a shape not yet released may
not appear on a test or a required deliverable" — and §2.2 releases the hexagon.

**But note what is not backing that up.** The natural second argument — that §2.2's
own graded gate already required a hexagon, so the test is only asking for what was
gated — is false: A2.2.0 as shipped charts a decision (see 2.6's *Timing* note). D1
may require the hexagon on the release rule alone, and should, because a loop charted
without one is the failure this part exists to catch. Just be aware that **2.6.1 and
2.7.4 are the first two places a hexagon is graded**, two days apart, with no graded
rehearsal behind either.

**Not released, must not appear:** the `[[ ]]` double-rail (§3.1), the connector
circle and the comment bracket (§4.1).

**2.7.4 must not copy 1.7.4's rule block.** 1.7.4 sets `min-process: 3` +
`min-decisions: 1` and no `min-nodes` — correct for a chart whose only shapes were
oval, rectangle and diamond, and wrong the moment a hexagon is legal, because
`min-process` counts rectangles only (`lib/diagram-check.ts:394`) and a student who
charts the loop properly can end up with two. 2.6 sets out the survey and the
replacement in full; **2.7.4 takes the same block as 2.6.1** — `min-nodes: 8`,
`min-process: 2`, `min-decisions: 1`, the other seven unchanged. Identical rules on
both charts is also the fairer arrangement when the PA is two days earlier and is
being handed back as the study guide.

**The printed syntax reference needs rebuilding for this chapter.** Ch 1's sheet was
declarations and the primitive types. Ch 2's is: the three loop forms, `break` and
`continue`, `switch`/`case`/`default`/`break`, `try`/`catch`/`finally`/`throw`, the
comparison and logical operators, and the Appendix D shape table including the
hexagon. Beginners are assessed on whether they can reason, not on whether they
memorised where `default` goes.

## Three forms, assigned automatically

Unchanged mechanism, restated so the module stands alone.

```
2.7.1 quiz ── variants: ["a","b","c"] ── hash(lessonId + student email)
                                              │
        ┌─────────────────────────────────────┼─────────────────────┐
        ▼                                     ▼                     ▼
   3 common concepts               3 common concepts       3 common concepts
   + 5 traces (form a)             + 5 traces (form b)     + 5 traces (form c)
        └──────── questions and options shuffled per student ───────┘
```

Eighteen questions authored; each student is asked eight. The five traces are the
same five *shapes* on every form — a `==` truthiness trap, a `for` with a step other
than 1, a `switch` fall-through, a nested loop, a `try`/`catch`/`finally` print order
— with different names and numbers, so the forms are genuinely equivalent.
`lib/quiz-variant.ts` does the assignment; `scripts/test-quiz.mjs` refuses to build a
quiz whose forms come out different lengths.

**Vary the numbers, never the trip.** A trace whose inner loop changes from `i` to
`i + 1` is a different question wearing the same shape, and that is the easy mistake
when authoring three forms of a loop rather than three forms of a straight line.

**But "vary the numbers" does not survive contact with the nested loop, and this is
the one place 1.7's mechanism does not simply carry over.** Chapter 1's five traces
were straight-line snippets: change the numbers and the student still reads the same
three or four lines, so workload was independent of the values. A nested loop's
workload *is* the values — 3 × 2 is six lines to write out and 4 × 2 is eight. Three
forms varying the bounds are the same skill at measurably different cost, on a timed
paper, assigned by a hash the student did not choose.

So for this trace **hold the product constant and vary the names and the body
expression instead.** Six lines factors only two non-degenerate ways (3 × 2 and
2 × 3), so the third form has to come from the body — `row + "-" + col` on one,
`row * col` on another — not from a third pair of bounds. A triangle
(`for (let j = 1; j <= i; j++)`) is *not* a third form: the inner bound depending on
the outer is a different trip by the rule above.

`scripts/test-quiz.mjs` refuses forms of different **length**. It cannot see any of
this, so it is an authoring discipline and nothing more.

**The other four lessons are single-form, deliberately**, for the reason 1.7 gives:
Part C's answer is typed into a file rather than picked from a list, and D1/D2 offer
a menu of three problems from which the student picks one.

## `summative` hides the key on screen; two other pieces keep it off the wire

**This is the half of 1.7 a reader of its module doc would never learn, and it is the
half that nearly lost the assessment.** `summative` governs what QuizView and
WrittenGrader *draw*. It does not govern what the page *ships*, and the difference is
not academic: `/lesson/[lessonId]/` is a statically exported page whose body is a
client component, so the whole `Lesson` object crosses the boundary and lands in the
RSC payload. Measured 2026-09-02 on `1-7-1`: View Source returned **all three forms,
all 18 `answer` indices and every explanation**, before a question had been answered.
Measured again 2026-09-03 on `1-7-2`: the `aiGrader.prompt` rubric — naming every
accepted answer — was still in the built page after WrittenGrader had stopped
rendering it.

Three pieces close that, all of them inherited, none of them automatic:

| Piece | What it does | Where 2.7 depends on it |
| --- | --- | --- |
| `lib/quiz-redact.ts` → `redactLessonForClient()` | Strips `answer`, `explanation` and `source` from a summative quiz; strips `prompt` and `contextDocs` from a summative `aiGrader` | **Called in the SERVER page** (`app/lesson/[lessonId]/page.tsx:8`, `app/assignment/[id]/page.tsx:8`) — after the `'use client'` boundary it is already serialised and too late |
| `scripts/score-quiz.mjs <lessonId>` | Turns picks into marks on the machine that still has the key | 2.7.1 — with the key gone the browser **cannot** mark, so the submission records picks and a NULL score |
| `fetchSubmissions` (server) in `WrittenGrader.tsx:144` | Decides "already submitted" from the server, not localStorage | 2.7.2 and 2.7.5 — 30 of the 100 points |

### The same leak is open on Part C today, and no check can see it

**`redactLessonForClient()` covers `quiz` and `aiGrader`. It does not touch
`requirements`** (`lib/quiz-redact.ts:84-93` — two branches, and that is the whole
function). `LessonWorkspace` is a client component that reads `lesson.requirements`,
and `app/assignment/[id]/page.tsx:35-38` hands it the "redacted" lesson, so every
`Requirement` — **including `pattern`** — crosses the boundary and is serialised.
That is the identical mechanism `lib/quiz-redact.ts:4-18` documents for the quiz.

**On a Find-and-Fix part the patterns are the answer key.** 1.7.3 is
`type: "assignment"` with `grading.summative: true`, and its five regexes hand over:

| Req | What View Source gives away |
| --- | --- |
| r1 | the closed-string form the unterminated literal has to become |
| r2 | both `beforTax` (the typo) and `beforeTax` (the fix), plus the required `total = beforeTax + tax` |
| r3 | `let shipping = 5;` — the corrected **value**, where the bug is the string `"5"` |
| r4 | `count = 2` as the thing that must not survive, and the `wrapFee` shape that must replace it |
| r5 | the three words being marked: `syntax`, `runtime`, `logic` |

The `title` and `hint` fields are the checklist the student is *meant* to see — the
symptom-only wording the 2026-09-02 narrowing settled. The patterns are not, and they
name the repair the narrowing deliberately stopped naming.

**`scripts/check-quiz-key-leak.mjs:52-53` collects only `lesson.quiz?.summative` and
`lesson.aiGrader?.summative`.** A `grading.summative` lesson is never collected and
the check has no notion of `requirements`, so the guard written for the first leak is
structurally blind to this one. `check-summative-parts.mjs` only asserts the flag is
*set*.

**This is live on 1.7.3 now; 2.7.3 inherits it by being authored the same way.** The
fix is the same shape as the quiz fix — strip `pattern` from a `grading.summative`
lesson's requirements before the client boundary, keep `title`/`description`/`hint`,
and teach `check-quiz-key-leak.mjs` to collect `grading.summative` and scan the built
page for each pattern. Part C's checker then cannot self-grade, which 2.7 already
assumes: shCode records, the teacher marks.

**Secondary, same class:** `redactLessonForClient` also ignores `diagram.aiGrader`.
1.7.4 has none, so nothing leaks today — but `2-2-12-a5-2-flowchart-decision` does
carry one, and if 2.7.4 is given a rubric its `prompt` ships unredacted.

Two consequences to plan for rather than discover:

- **Part A's marks do not exist until you run `score-quiz.mjs`.** Budget that; it is a
  step between the period ending and a number going in Aeries, and it is not optional.
  `lib/quiz-answer-key.mjs` prints the key for the parts you mark by hand.
- **`stripKey()` is a rebuild, not a delete.** It names the fields it keeps — `id`,
  `question`, `options`, `code`, `variant` — so **a question that grows a new
  key-bearing field must be added there on purpose**. If 2.7.1's traces want a field
  1.7's did not have, that is the file to check before the day, not after.

The `summative`-drops-the-lock argument is also where the second lock came from:
`WrittenGrader` read localStorage alone, so clearing site data, switching browser or
opening a second device handed back an unlocked Submit on an assessment that has no
retake. 2.7 has no retake either.
