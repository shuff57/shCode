# Module 7.1: Synthesis (Game Capstone)

**Quarter 2 · ~3.5 contact hours in class + homework**
**Environment:** moSHion in-app editor.

- **SLO 3 PRIMARY Sem 1 evidence (A18.1 Game Capstone)**: design + implement + test cycle

- Contributes to **SLO 2** (classes + state machines in a shipped product)

## Unit Goal
Students ship a complete game that they designed themselves. The unit is entirely build + test + iterate + showcase. This is the Semester 1 closing artifact: the teacher retains design docs, testing logs, and reflections for dual-enrollment documentation.

## Shape of this module

A performance task, not a guided build. There is no reading, no worked example
and no starter game: the module is a checklist of twelve things the game must
contain, drawn from every unit behind it, and nothing at all about what the game
should be. Two students can tick every box and hand in games with nothing in
common. That is the point: the checklist measures what they can reach for
unprompted, which is the one thing a scaffolded project cannot.

The checker is capability-level on purpose. It looks for *a* class, *a* Group,
*a* function that takes a parameter and returns a value, never a particular
name, because a checker that pins names would quietly turn a design task back
into a fill-in-the-blanks one.

## Inter-module bridges
- **Modules 5.1–6.8 → 7.1.1:** Every prior moSHion module contributes directly. The checklist *requires* a custom class (5.4), a Group (6.1), an overlap or collision (6.2), persistent storage (6.5), and three game states (6.6), plus functions, arrays and manual testing carried over from Q1. Animated sprites (6.4) and joints (6.8) sit in the choose-any-two item rather than the required list, since 6.7's own notes say most students will not master joints.
- **Module 7.1 → Sem 2 (Q3):** None: clean quarter break. Semester 2 starts with a fresh environment (JSCAD).
