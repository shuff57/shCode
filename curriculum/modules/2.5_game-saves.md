# Unit 2.5 — Game Saves

**Quarter 2 · ~3.5 contact hours**
**Environment:** q5play in-app editor.

## SLO Focus
- **SLO 3** primary (File I/O — A16.1 Save System is the SLO-3 artifact)
- Covers the Butte outline topic **File I/O (secondary location after W8 FileReader)**

## Unit Goal
Students give their q5play games the one thing they're missing to feel like real games: data that survives a refresh. The unit walks `storeItem` / `getItem`, the type-coercion trap, JSON serialization, save slots, and auto-save / continue patterns. A16.1 ships a complete save system on top of the Unit 2.4 game.

## Inter-module bridges
- **Unit 2.4 → 2.5.1:** The platformer / side-scroller from 2.4 gets a persistent save layer bolted on.
- **Unit 2.5 → Unit 2.6:** Saves are the data layer; Unit 2.6 (Game States) is the flow layer that decides *when* to save. A16.2 in 2.6 explicitly integrates the save system from A16.1.

## Pre-requisite snapshot
- Has a Unit 2.4 game (platformer / side-scroller) to bolt persistence onto.
- Arrays + JSON object-literal familiarity (Q1 fundamentals).

## Post-requisite snapshot
- Can write and read single values with `storeItem` / `getItem`, including the `Number(getItem(...))` coercion.
- Can round-trip a structured object through storage via `JSON.stringify` / `JSON.parse`.
- Can manage multiple save slots (read, write, delete, overwrite).
- Has a Title screen that detects existing saves and offers New Game / Continue.
- Has a working auto-save (checkpoint or timer-driven) on the Unit 2.4 game.
- Knows `loadJSON` is async and lives in `preload()`.

None at unit close — A16.1 is the unit's graded artifact.
