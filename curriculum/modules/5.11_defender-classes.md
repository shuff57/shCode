# Module 5.11: Project — Defender, Part C (classes clean it up)

**Quarter 2 · the capstone's third part · after §5.10 Defender, Part B**

## SLO Focus
- **SLO 3:** the module's artifact is the complete, playable Defender.
- **SLO 2:** the same game rebuilt with classes: `Bullet`, `Enemy` and `Spawner`.

## Module Goal
Students rebuild their Part B game as three classes with the same behaviour, then playtest it, check it and extend it. The new idea is **refactoring**: same game, same numbers, rules moved to the objects that own them. The three parallel arrays become one array of `Enemy` objects, the nested hit loop loses every `splice` and its `break`, and the wave globals become one `Spawner`. **No groups and no `extends`**: 6.1 teaches groups.

## Pre-requisite snapshot
§5.10 complete: parallel arrays kept in step, a nested hit loop that splices safely, waves with a pause, and the 5.10.8 drift bug found and fixed. From 5.8: `takeHit` with a floor, `isAlive()`, a method whose parameter is another object, `filter`, `static spawned`.

## Post-requisite snapshot
Can refactor working procedural code into classes without changing what it does, keep removal in one place, use one object's method on another, own a timer inside a class, and reset a class variable on restart. Ready for 6.1, where a `Group` does the list-keeping.

## Note
**Not a book section.** The third and last part of the Defender capstone (5.9 ship and shots, 5.10 enemies and waves, 5.11 classes). Spec: `codehs-review/CAPSTONE-SPEC.md` §6. It closes the capstone with the written playtest-and-reflect (5.11.7, AI-graded) and the challenges (5.11.9).

**9 lessons** (`5.11.1`-`5.11.9`) in folders `5-11-defender-*`. Each lab's starter is the previous lab's solution with one class skeleton added (5.11.4 starts from the Part B final), and each solution was checked to play exactly as Part B did: the same autopilot run gives the same score, base and wave after 5.11.4, after 5.11.5 and at the end.

**Words on screen go in `drawTop()`**, the convention 5.4 set and Part A repeated: the score, the wave, the base and the game-over lines (now with "enemies faced") are drawn there, after the sprites, so no enemy can cover them.

**The checklist, said aloud.** `Spawner` answers "no" to 5.7.18's first question (there is only one). 5.11.1 says so and gives the reason it is a class anyway: its facts change together, so a restart is one line, `spawner = new Spawner()`, that cannot forget a piece. 5.11.2 asks for it and 5.11.8 q6 checks it.

### The one idea this module is really about
**Finished in one place.** Inside the frame, objects only change their own state (`takeHit`, `land`, `spend`); nothing is spliced inside a loop. Once, at the end of the frame, each list is cleared in two places, in order: `remove()` every finished one (the screen), then `filter` to keep the alive ones (the list). 5.11.3 teaches it and 5.11.4-5.11.5 use it.
