# Module 2.6.1 — Game States

> **Q2 Game States · 3.5 contact hours (2 sessions) · Environment: q5play in-app editor**
> **SLO focus:** SLO 3 (structured programming via state machines) — reinforces SLO 2 (one variable owns flow).
> **Audience:** introductory CS students — for most, `switch` is rusty from Q1 and state-machine-as-structure is a new mental model. **Granularity bar applies** (`sub-module-spec-conventions.md` §2a): one new concept per lesson.

## Context

This unit gives the q5play game a *shape*. Three big ideas:
1. **One variable owns the flow** — `let gameState = 'title'` is the single source of truth.
2. **`switch` dispatches per frame** — `switch (gameState)` at the top of `draw()` so each `case` owns its render + input.
3. **Transitions are how the game moves** — input-driven (`kb.presses` → state change) and condition-driven (score / lives threshold → state change), each placed inside the `case` whose state owns them.

A16.2 is the integration artifact — a 4+ state machine (title / play / pause / gameover or win) wired into the save system from A16.1 so saves trigger on transitions and Continue loads into the right state.

**Audience.** Per the granularity bar, every reading and try-it owns exactly **one** atomic concept; integration happens only inside the worked examples and A16.2. The `switch` cluster (2.6.3 / 2.6.4 / 2.6.6) reinforces a syntactic form first introduced in Q1 conditionals — students who are rusty get fresh single-concept pages before it's used as the state-dispatch tool.

**Do NOT:**
- Let students implement state via a giant `if`-chain — push toward `switch`.
- Drop transitions in the wrong `case` body — `'menu' → 'play'` is logic for `case 'menu'`, not `case 'play'`.
- Use `kb.pressing(...)` for one-shot transitions — flips every frame the key is held; use `kb.presses(...)`.
- Compound the state machine and save integration into one lab without intermediate single-concept worked examples first.

> **Cross-unit handoff:** the save layer was built in **Unit 2.5 (Game Saves)**, A16.1. This unit reuses it; it does not re-derive `storeItem` / `JSON.stringify`. New work is exclusively about flow.

## Learning Objectives

Students will be able to:
1. Read a `switch` statement and pick the correct `case` for a given value.
2. Use `break` to terminate each case; explain the fall-through trap.
3. Declare a state variable (`let gameState = 'title'`) as the single source of truth for game flow.
4. Name states with conventional labels (`'title'`, `'play'`, `'pause'`, `'gameover'`, `'win'`).
5. Drive `draw()` with `switch (gameState)` so each state owns its render + input logic.
6. Write a transition triggered by **input** (e.g. `kb.presses(' ')` → `gameState = 'play'`).
7. Write a transition triggered by a **game condition** (e.g. `score >= 10` → `gameState = 'win'`).
8. Compose three or more states into a working game flow (title → play → gameover → title).
9. Extend to 4+ states with pause, win, or another screen using the same pattern.
10. Trigger a save (`storeItem` + `JSON.stringify`) on a state transition.
11. Restore state on Continue — load the saved data AND set `gameState` to the right value.

## Topics Covered

Each bullet is a single atomic concept and corresponds 1:1 to a Numbered Lesson List slot.

**`switch` foundations:**
- `switch` syntax — `case`, `break`, fall-through.
- `switch (gameState)` inside `draw()` — state dispatch.
- `break` and `default` — exit and catch-all.

**State variable:**
- `let gameState = '...'` as the single source of truth.
- Naming conventions for states.
- "One variable, many screens" mental model.

**Transitions:**
- Input-driven transitions (`kb.presses → gameState = ...`).
- Condition-driven transitions (score / lives / timer → `gameState = ...`).

**Composition:**
- Three-state machine: title → play → gameover.
- Extended states: pause, win, settings, inventory.

**Save integration (reuse of Unit 2.5):**
- States decide *when* to save — autosave on transitions.
- Continue loads the right state, not just the right data.
