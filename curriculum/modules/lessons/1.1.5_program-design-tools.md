# Sub-Module 1.1.5 — Program Design Tools and Environments

> **Book §1.5 · 3 class days · Environment: browser console · Q1 Unit 1.1 Foundations**
> **SLO focus:** SLO 4 primary (process as algorithm / computational thinking); reinforces SLO 2 (debugging and code quality).
> **Granularity bar:** each lesson ships exactly one new concept.

## Context

Book §1.5 closes Chapter 1 and closes Unit 1.1. It is the richest section in the chapter — nine subsections covering computational thinking's four techniques, pseudocode, flowcharts, recursion, where JavaScript actually runs, and how to read an error message and debug. This is deliberately the most content-dense sub-module in the unit; §2a's guidance to "count the concepts first, then say how many days they take" pushes this one to the full 3-day ceiling rather than the 2-day estimate a chapter-count-only plan might assume.

The audience is intro-level, same as the rest of Unit 1.1, but this section asks for a different kind of thinking than 1.1.2–1.1.4 did: instead of vocabulary about *what exists* (types, paradigms), this section is about *how to plan before typing* — a skill, not a fact. Give the jam-sandwich thread (decomposition → pattern recognition → abstraction → algorithm) the room the book gives it; it is the throughline that makes four otherwise-abstract concepts concrete.

**Do NOT:**
- Rush recursion (§1.5.6). It is genuinely advanced material this early in the course — flag the pacing risk to the teacher (see Teacher Notes) rather than compressing it to fit a tighter schedule.
- Silently duplicate Unit 1.2's existing algorithm/pseudocode content. Unit 1.2 (Control Flow, book Chapter 2) already ships readings at slots `1.2.17`–`1.2.19` ("What Is an Algorithm?", a pseudocode-to-code worked example, an algorithm writeup) — authored independently of the book, not derived from §1.5. This sub-module's algorithm/pseudocode readings (1.1.54–1.1.55) are the book-aligned, *pre-control-flow* treatment (sequence only, no `if`/loops to translate into yet); Unit 1.2's readings are the *post-control-flow* reinforcement, where pseudocode can finally become real branching/looping code. Framed this way the two are legitimate spaced repetition, not waste — but say so explicitly to a teacher building both, so it reads as intentional.
- Treat `console.log`-based debugging (§1.5.9) as review. Students have used `console.log` to print values since 1.1.1, but using it *specifically to locate a bug* — printing what you believe is true and checking it — is a new, teachable habit, not a restatement of syntax already known.

## Learning Objectives

Students will be able to:

1. Define computational thinking and name its four techniques.
2. Decompose a problem into smaller parts and group those parts by pattern.
3. Apply abstraction — keep only the details relevant to the problem at hand.
4. Define "algorithm" and write pseudocode for a simple task.
5. Read the three flowchart shapes and translate a simple decision into one.
6. Distinguish parallel from concurrent execution.
7. Explain what a base case is and why a recursive function needs one.
8. Explain the difference between the browser console and a code editor, and when to use each.
9. Read an error message and identify its three parts.
10. Use `console.log` deliberately to find out what a program is actually doing, not just what it prints.

### Reading content guidance

#### R1 — What Is Computational Thinking? (`1-1-5X-reading-computational-thinking`)

- **Topic 1: A problem-solving process with four techniques** — read before every other reading in this sub-module; it's the map for all of them.
  - Computational thinking breaks a complex problem into smaller, manageable parts and devises systematic approaches to solve them.
  - The four techniques (this book's framing): decomposition, logical thinking/pattern recognition, abstraction, algorithms. (Note for the teacher: this reading names all four; R2–R4 each teach one in depth — R2 covers two of the four at once, matching how the book pairs them.)
  - The "three As" shorthand: abstraction (formulate), automation (express the solution), analysis (execute and evaluate).
  - Introduce the jam-sandwich thread here: a programmer instructing a robot to make a sandwich, where every unstated assumption a person would skip has to be written down. This example carries through R2 and R3.
  - **Try it:** book's own Try It Now 1.1 — list five instructions for a robot making a jam sandwich, then read the list back taking every instruction literally. Which one breaks first? (No code — this is a plain-language exercise, matching the book's own zero-code treatment here.)
- **Glossary rows:** computational thinking, complex problem.

#### R2 — Decomposition and Pattern Recognition (`1-1-5X-reading-decomposition`)

- **Topic 1: Breaking a problem apart, then grouping what you find** — the book treats these two as a matched pair (decomposition finds the pieces; pattern recognition sorts them into categories), so this reading keeps them together rather than splitting further — the same reasoning already used for 1.1.3's comments reading.
  - Decomposition: break a complex problem into smaller, self-contained parts.
  - Pattern recognition: group what decomposition turned up into categories (ingredients / equipment / actions, for the sandwich).
  - Briefly name inductive vs. deductive reasoning as the two ways programmers find patterns — a light touch is enough here, not a full logic lesson.
  - **Try it:** book's own Try It Now 1.2 — decompose "get to school on time tomorrow" into at least six tasks, then group them into two or three categories.
- **Glossary rows:** decomposition, pattern recognition, inductive reasoning, deductive reasoning.

#### R3 — Abstraction (`1-1-5X-reading-abstraction`)

- **Topic 1: Keeping what matters, dropping what doesn't** — single-topic reading.
  - Abstraction is a simplified representation that keeps only the details relevant to the problem at hand.
  - Context Pause: you already trust abstraction constantly (driving a car without knowing how the engine mixes fuel).
  - The test for whether a detail can be dropped: does removing it change the action the reader has to take?
  - **Try it:** book's own Try It Now 1.3 — describing a bus route to someone who's never been to town: name two details to keep and two to drop, and say why.
- **Glossary rows:** abstraction.

#### R4 — Algorithms and Pseudocode (`1-1-5X-reading-algorithms-pseudocode`)

- **Topic 1: An algorithm is a plan, and pseudocode is how you write one down before it has a language** — single-topic reading pairing two tightly-linked definitions.
  - An algorithm is a finite, ordered sequence of unambiguous instructions.
  - Pseudocode describes those steps in plain language, arranged like code, with indentation showing containment — but it is not runnable in any language.
  - Two conventions: one instruction per line; indent what's inside something else.
  - Context Pause: no compiler checking pseudocode is the point — a syntax error tells you nothing about whether the plan makes sense.
  - **See Context above** for why this reading's scope stays pre-control-flow (sequence only) even though the book's own butter-or-no-butter example uses `IF`/`ELSE` — present that example as a preview of what pseudocode *can* express once Unit 1.2 teaches selection, not as something the student writes themselves yet.
  - **Try it:** book's own Concepts in Practice check — spot the bug in a pseudocode loop that never terminates (`count` never changes) — this only requires reading pseudocode, not writing branching pseudocode, so it fits before control flow.
- **Glossary rows:** algorithm, pseudocode.

#### R5 — Flowcharts (`1-1-5X-reading-flowcharts`)

- **Topic 1: The same plan, drawn as a picture** — single-topic reading.
  - Three shapes: oval (start/end), rectangle (a step), diamond (a decision, one way in and two ways out).
  - Pseudocode is faster to write; a flowchart is easier to see, especially for branching.
  - **Try it:** book's own Try It Now 1.5 — sketch a flowchart for "get a number; if even print 'even', otherwise print 'odd'" and name the shape used at each step (description-only, since drawing isn't a console exercise — this reading's Try-it is a written/verbal exercise, not a `js live console` block).
- **Glossary rows:** flowchart, decision (diamond).

#### R6 — Parallel and Concurrent Execution (`1-1-5X-reading-parallel-concurrent`)

- **Topic 1: Two ways to make an algorithm finish sooner** — single-topic reading, kept brief (the book itself points forward to a later chapter for depth).
  - Parallel: genuinely simultaneous, needs multiple processors.
  - Concurrent: simulated simultaneity on one CPU by switching between tasks quickly.
  - The two-ticket-lines analogy (splitting up to buy movie tickets faster) is the book's own hook — reuse it.
  - **Try it:** none — this reading is conceptual scene-setting for R7 (recursion), which is where the sub-module's runnable code returns. A short "name a task in your own life that's easier done in parallel than alone" written prompt is sufficient.
- **Glossary rows:** parallel execution, concurrent execution.

#### R7 — Recursion (`1-1-5X-reading-recursion`)

- **Topic 1: A function that calls itself on a smaller version of the problem** — single-topic reading; the most conceptually demanding reading in this sub-module (see Teacher Notes on pacing).
  - Recursion needs a base case — an input simple enough to answer directly, ending the chain of calls.
  - Without a base case: stack overflow (`RangeError: Maximum call stack size exceeded`).
  - Frame as two claims, not a loop: the base case is the simplest version of the problem; the recursive step is "the answer to this input is X plus the answer to a smaller input."
  - Insight Note: deferred, not repeated — the pending calls are held in memory until the base case lets the chain unwind.
  - **Try it:** book's own Try It Now 1.6 — run a `recursiveSum` function missing its base case, watch it throw `RangeError`, then add the missing base case so it correctly prints 55. Causing the crash on purpose is the point — students should recognize a stack overflow later because they triggered one here first.
- **Glossary rows:** recursion, base case.

#### R8 — The Console and a Code Editor (`1-1-5X-reading-console-editor`)

- **Topic 1: A scratchpad vs. a place programs live** — single-topic reading.
  - The developer console (F12 → Console) runs JavaScript immediately; everything typed is forgotten on reload.
  - A code editor holds programs you intend to keep, with syntax coloring and indentation help.
  - The in-app editor students have used since 1.1.1 is, in this framing, a console *and* an editor at once — a deliberate convenience, still ordinary JavaScript underneath.
  - **Try it:** book's own Try It Now 1.7 — type `2 + 2 * 3` then `(2 + 2) * 3` and compare the two answers; the point isn't the arithmetic, it's noticing how fast the console settles a question.
- **Glossary rows:** developer console, code editor.

#### R9 — Reading an Error Message (`1-1-5X-reading-error-messages`)

- **Topic 1: Three parts worth reading** — single-topic reading.
  - The kind (e.g. `ReferenceError`), the detail (what it couldn't find), the place (line number).
  - Context Pause: "it doesn't work" isn't a description; "it says `ReferenceError: totl is not defined` on line 3" both describes the problem and often answers it.
  - **Try it:** book's own Try It Now 1.8 — run code with a misspelled variable (`gretting` vs `greeting`), read the `ReferenceError`, identify which of the three parts solved it, then fix the typo.
- **Glossary rows:** error message, `ReferenceError`.

#### R10 — Testing and Debugging (`1-1-5X-reading-testing-debugging`)

- **Topic 1: Comparing what you believe against what actually happens** — single-topic reading, the capstone of the whole sub-module.
  - Testing uses test cases — specific inputs that check whether a program meets its requirements.
  - Debugging: print what you *believe* is true and check it. Most bugs aren't crashes — the program runs and prints a wrong answer with no error at all.
  - Two habits: label every print (`console.log("total is " + total)`, not a bare `console.log(total)`); print more than you think you need.
  - **Try it:** book's own Try It Now 1.9 — a rectangle-area program that should print 20 but has `+` where it needs `*`. Add labeled `console.log` lines for each input, use them to rule out the inputs, and find the mistake is in the combining line.
- **Glossary rows:** test case, debugging, `console.log` (as a debugging tool, distinct from its printing-output role taught in 1.1.1).

## Worked Examples (teacher-led)

### Worked Example 1 — Writing Pseudocode for a Decision (10 min)

Book §1.5.4's voting-age example, run live right after R4. Project this pseudocode:

```
ask the user for their age
if age is 18 or more
    print "You may vote"
otherwise
    print "Too young to vote"
```

Read it aloud as if to someone who has never coded — the point is that it's right or wrong on its own terms, checkable by reading, with nothing yet about *how* to ask or what a variable is. Then extend it live with the book's butter-or-no-butter branch (`INPUT`/`IF`/`THEN`/`ELSE`) to show pseudocode handling a real decision — explicitly flagged to students as a preview of what Unit 1.2 makes runnable.

## Assignments

### A5.1 — Computational Thinking Applied (written, AI-graded)

- **Type:** written response. Primary SLO-4 evidence artifact — retain.
- **Est. time:** 30 min, out of class.
- **Task:** pick a problem from daily life (not programming) and walk it through all four computational-thinking techniques — decomposition, pattern recognition, abstraction, and a short algorithm (numbered steps) for solving it. Matches the book's own budget-planning example structure.
- **Requirements:** all four techniques named and applied to the chosen problem; the algorithm step is a genuinely ordered, numbered list (not prose).
- **Pass criteria:** every requirement present. Mastery-graded — resubmit until green. Not scored on writing quality.

### A5.2 — Debug the Broken Program (lab)

- **Type:** console lab. Support artifact, reinforces SLO-2.
- **Est. time:** 15 min.
- **Task:** given a short program with one logic bug (an operator error, mirroring the book's own rectangle-area example) and no syntax error, add labeled `console.log` statements to isolate which variable holds the wrong value, then fix the bug.
- **Requirements:** at least two labeled `console.log` calls present (regex: `console\.log\(.*["'].*["'].*\+`, checking for a string-labeled print, not a bare value); the final output matches the corrected expected value.
- **Pass criteria:** all-green Submit gate. Mastery-graded — resubmit until green.

## Vocabulary

| Term | Definition |
|---|---|
| computational thinking | A problem-solving process that breaks a complex problem into smaller parts and devises systematic approaches to solve them. |
| decomposition | Breaking a complex problem into smaller, self-contained parts. |
| pattern recognition | Grouping the parts decomposition turned up into categories. |
| abstraction | A simplified representation that keeps only the details relevant to the problem. |
| algorithm | A finite, ordered sequence of unambiguous instructions that solves a problem. |
| pseudocode | A program's steps written in plain language and arranged like code; not runnable. |
| flowchart | A diagram of a program's steps using ovals, rectangles, and diamonds connected by arrows. |
| recursion | A technique where a function calls itself on a smaller version of the same problem, stopping at a base case. |
| base case | The input simple enough for a recursive function to answer directly, ending the chain of calls. |
| developer console | The browser panel for running JavaScript immediately and reading output/errors. |
| ReferenceError | The error raised when a name is used that doesn't exist — usually a typo or missing declaration. |
| debugging | Finding and fixing incorrect behavior by comparing what you believe a program does with what it actually does. |

## Teacher Notes

- **Recursion (R7) is a real pacing risk.** It is genuinely advanced material for Q1 Week ~3 of an intro course — stack overflows, base cases, and "deferred, not repeated" execution are a lot for students who wrote their first `let` three sub-modules ago. Consider this an explicit flag rather than a silent inclusion: if the class is behind, this is the reading to slow down on rather than cut, since the book gives it a full subsection and a dedicated Try-it (not filler).
- **The Unit 1.2 overlap (R4) is intentional, not a bug — but say so out loud.** A student who reaches Unit 1.2's `1.2.17` reading a few weeks after this sub-module should experience it as "oh, I remember pseudocode — now I get to make it branch," not as unexplained repetition. One sentence bridging the two when Unit 1.2 opens is enough.
- **R6 (parallel/concurrent) has no Try-it on purpose** — it's scene-setting for recursion, not a skill to practice in isolation this early.
- **A5.1's problem choice is free.** Encourage genuinely varied topics (a chore, a game strategy, a recipe) — grading four named techniques present, not the topic's polish, per the mastery-based rule.
