# Module 2.4.1 — Animated Sprites and Camera

> **Week 15 · Q2 Animation & Camera · 3.5 contact hours (2 sessions) · Environment: q5play in-app editor**
> **SLO focus:** Reinforces SLO 3. Adds polish and scale needed for a capstone-worthy game.
> **Audience:** introductory CS students — for most, this is first encounter with sprite animations as state-driven swaps AND with the camera as a coordinate transform. **Granularity bar applies** (`sub-module-spec-conventions.md` §2a): one new concept per lesson; multi-concept readings are split into sub-letter atomic rows.

## Context

Week 15 transforms a static-canvas sketch into a scrolling world with animated characters. Two big ideas: **sprite animations** (swap frames based on state) and **camera** (world larger than canvas, view follows the player). Camera math confuses students until they see it visually — lead with the analogy "the world doesn't move, your window does." This module also hosts the AP CSP discussion on digital image representation (sprite = pixel grid + RGBA).

**Audience.** Most students are seeing the q5play animation API and the camera-as-transform model for the first time. Per the granularity bar, each reading owns exactly one of `addAni` / `changeAni` / `frameDelay` / `sprite.image` (animation cluster) and one of `camera.x-y` / camera-follow / `lerp` / `sprite.layer` (camera cluster). Integration of multiple atomic concepts happens only inside the worked examples and the A15.1 platformer lab. The granularity refactor was applied retroactively after the original build (which shipped two multi-concept readings); existing integer slugs (`2-4-3-reading-animation`, `2-4-7-reading-camera`) are preserved as the trimmed parents while new atomic concepts land under sub-letter slugs (`2-4-3a-…`, `2-4-7a-…`) per §4.1 (data-safety: existing student commits keep their FK against the integer slugs).

**Do NOT:**
- Go deep on sprite sheets — q5play's `addAni(name, url1, url2, ...)` with individual image frames is the simpler default.
- Teach parallax scrolling — that's stretch material.
- Bundle `addAni` + `changeAni` + `frameDelay` + `sprite.image` into one "Animation reading" — that's the multi-concept bundling the granularity pass exists to prevent.
- Bundle `camera.x/y` + camera-follow + `lerp` + `layer` into one "Camera reading" — same anti-pattern as above.

## Learning Objectives

Students will be able to:
1. Register a named animation on a sprite with `sprite.addAni(name, frame1, frame2, ...)` and recognize that the first registered animation becomes active by default.
2. Swap a sprite's active animation with `sprite.changeAni(name)`.
3. Control animation cycle speed with `sprite.animation.frameDelay = N`.
4. Display a single still image on a sprite with `sprite.image = url`.
5. Drive an animation swap from input state (`kb.pressing(...) → changeAni(...)`).
6. Move the camera viewport with `camera.x` / `camera.y`.
7. Implement a camera-follow pattern that tracks the player horizontally.
8. Smooth a follow camera using `lerp(current, target, t)`.
9. Control sprite render order with `sprite.layer = N` and explain why HUD elements use a high layer.
10. Explain that the camera is a coordinate transform, not a "real" object — the world stays put, only the viewport moves.

## Topics Covered

Each bullet is a single atomic concept and corresponds 1:1 to a Numbered Lesson List slot.

**Animation:**
- `sprite.addAni(name, frame1, frame2, ...)` — register a named animation.
- `sprite.changeAni(name)` — swap active animation between registered names.
- `sprite.animation.frameDelay = N` — control cycle speed.
- `sprite.image = url` — single-frame still art (no animation).

**Camera:**
- `camera.x` / `camera.y` — viewport center coordinates.
- Camera-follow pattern — `camera.x = player.pos.x` (or with offset).
- Smoothing with `lerp(current, target, t)`.
- `sprite.layer = N` — render order (higher = drawn on top).

### Reading content guidance

Per `reading-conventions.md` §3 — every reading opens straight into per-topic `## <Topic>` subsections, each with a `js live` Try-it block, and ends with a glossary table. Most atomic readings own exactly one topic; the trimmed parents (R1, R2) ship a single mental-model topic.

#### R1 — Animation overview (`2-4-3-reading-animation`, parent — trim)

- **`externalLink`:** `/docs/q5play/animation`.
- **Topic 1: A sprite can have multiple animations; one is active at a time** — read before `2.4.3a Reading — addAni`.
  - **What you'll learn from it:** sprites carry an animation library indexed by name; only one animation renders per frame (the active one); state-driven games swap between named animations to express what the player is doing (idle, run, jump); concrete API names (`addAni`, `changeAni`, `frameDelay`, `sprite.image`) each have their own focused reading next.
  - **Try it:** spawn one sprite with default rendering (no `addAni` calls) — `new Sprite(200, 200, 40, 40)`. Student observes the default colored rectangle and reads the inline note that everything in the sub-letter readings replaces or extends this default.
- **Glossary rows from §Vocabulary:** `Animation`, `Frame (animation)`.

#### R1a — `addAni(name, frame1, frame2, ...)` (`2-4-3a-reading-add-ani`)

- **`externalLink`:** `/docs/q5play/animation`.
- **Topic 1: Registering a named animation** — read before `2.4.3b Reading — changeAni`.
  - **What you'll learn from it:** `sprite.addAni(name, frame1, frame2, …)` registers a named animation on this sprite; frames can be image URLs or — for in-class without art assets — a single placeholder image used N times to "pad" the cycle; the **first** `addAni` call also becomes the sprite's active animation, so register the default first.
  - **Try it:** one sprite. `player.addAni('idle', '/q5play/img/idle.png')` (use a placeholder URL or a base64 dot if no art). The sprite renders with the registered frame instead of the default colored rectangle.
- **Glossary rows from §Vocabulary:** `Active animation`, `Frame (animation)`.

#### R1b — `changeAni(name)` (`2-4-3b-reading-change-ani`)

- **`externalLink`:** `/docs/q5play/animation`.
- **Topic 1: Swap the active animation** — read before `2.4.4 Worked Example — Animating a Sprite`.
  - **What you'll learn from it:** once two or more animations are registered, `sprite.changeAni(name)` swaps which one renders; calling `changeAni('foo')` for an unregistered name is a no-op (silent failure) — register *before* you switch; the swap is instant — there's no transition.
  - **Try it:** register `'idle'` and `'run'`; in `draw`, `if (kb.pressing('right')) player.changeAni('run'); else player.changeAni('idle');`. Student presses Right and watches the swap.
- **Glossary rows from §Vocabulary:** `Active animation`.

#### R1c — `frameDelay` (`2-4-3c-reading-frame-delay`)

- **`externalLink`:** `/docs/q5play/animation`.
- **Topic 1: Slow or speed the animation cycle** — read before `2.4.5 Animated Sprites Sandbox`.
  - **What you'll learn from it:** `sprite.animation.frameDelay = N` sets the number of game frames each animation frame holds (higher N = slower cycle); default is 4; the property lives on the *active animation*, so set it after `changeAni` if you want per-state pacing; doesn't affect single-frame art (where the cycle never advances).
  - **Try it:** start from the R1b sketch with the run animation active. Set `player.animation.frameDelay = 12` while running and `frameDelay = 4` while idle. Student observes the cadence change.
- **Glossary rows from §Vocabulary:** `frameDelay`, `Cycle speed`.

#### R1d — `sprite.image` (`2-4-3d-reading-sprite-image`)

- **`externalLink`:** `/docs/q5play/animation`.
- **Topic 1: Single-frame art** — read before `2.4.5 Animated Sprites Sandbox`.
  - **What you'll learn from it:** for sprites that don't need an animation, `sprite.image = '/path/to/file.png'` displays a single still image — no `addAni` calls, no cycle; useful for HUD elements, level decorations, and one-off props; mutually exclusive with the animation system on a given sprite (use one or the other).
  - **Try it:** a static ground sprite (`new Sprite(200, 380, 400, 20, 'static')`). Set `ground.image = '/q5play/img/ground.png'`. Student verifies the still image renders without animating.
- **Glossary rows from §Vocabulary:** `Still art`.

#### R2 — Camera as transform (`2-4-7-reading-camera`, parent — trim)

- **`externalLink`:** `/docs/q5play/camera`.
- **Topic 1: The world doesn't move — your window does** — read before `2.4.7a Reading — camera.x / camera.y`.
  - **What you'll learn from it:** the canvas always shows a viewport into a coordinate space; sprites have absolute world coordinates; the camera object holds the *center* of the viewport; assigning `camera.x` / `camera.y` shifts what's rendered without moving any sprite; the flashlight analogy lands here — the room is dark and full of stuff, your flashlight points at one patch at a time.
  - **Try it:** static scene with five sprites at `x = 100, 200, 300, 400, 500`. Default camera shows the centred range. Student manually edits `camera.x = 400` and reloads to verify the view shifted without changing any sprite's `pos.x`.
- **Glossary rows from §Vocabulary:** `Camera`, `Viewport`, `World coordinates`.

#### R2a — `camera.x` / `camera.y` (`2-4-7a-reading-camera-xy`)

- **`externalLink`:** `/docs/q5play/camera`.
- **Topic 1: Moving the viewport** — read before `2.4.7b Reading — Follow pattern`.
  - **What you'll learn from it:** `camera.x` and `camera.y` are the *center* of the visible area; their default of `(canvas.w/2, canvas.h/2)` keeps the viewport centred on the world's `(0, 0)` start; assigning new values shifts the view; the change takes effect on the *next* frame's render.
  - **Try it:** spawn a long static row (`new Sprite(x, 200, 30, 30)` for `x` from `0` to `1500` step `100`). In `draw`, `camera.x += 1`. Student watches the row scroll past horizontally.
- **Glossary rows from §Vocabulary:** `camera.x` / `camera.y`.

#### R2b — Camera-follow pattern (`2-4-7b-reading-camera-follow`)

- **`externalLink`:** `/docs/q5play/camera`.
- **Topic 1: Locking the viewport to a sprite** — read before `2.4.8 Worked Example — Camera Follow`.
  - **What you'll learn from it:** the canonical follow pattern is `camera.x = player.pos.x;` placed inside `draw()` — every frame the camera centers on the player; an offset like `camera.x = player.pos.x - canvas.w / 2 + 100` keeps the player off-center if your gameplay needs it; the player never visually moves on the canvas — the world scrolls under them.
  - **Try it:** R2a's static row + a player sprite at `(100, 200)` that moves right with `kb.pressing('d') → vel.x = 4`. Add `camera.x = player.pos.x;` to `draw`. Student walks right and sees the world scroll while the player stays centered.
- **Glossary rows from §Vocabulary:** `Follow camera`.

#### R2c — Smoothing with `lerp` (`2-4-7c-reading-lerp-smoothing`)

- **`externalLink`:** `/docs/q5play/camera`.
- **Topic 1: Smooth follow with lerp** — read before `2.4.9 Worked Example — Smooth Camera with lerp`.
  - **What you'll learn from it:** `lerp(current, target, t)` returns a value `t`-fraction of the way from `current` to `target`; replacing the hard-set `camera.x = player.pos.x` with `camera.x = lerp(camera.x, player.pos.x, 0.1)` makes the camera trail the player like it's on a stretchy spring; small `t` (0.05–0.1) gives a smooth lag, large `t` (0.5+) snaps quickly; `lerp` is also useful anywhere you want eased motion (UI, value blending).
  - **Try it:** start from the R2b sketch. Replace the hard-follow line with `camera.x = lerp(camera.x, player.pos.x, 0.1);`. Student edits `t` to `0.05`, `0.1`, `0.5`, and reloads each time to feel the difference.
- **Glossary rows from §Vocabulary:** `lerp()`, `Easing`.

#### R2d — `sprite.layer` (`2-4-7d-reading-sprite-layer`)

- **`externalLink`:** `/docs/q5play/camera`.
- **Topic 1: Drawing a HUD on top of the world** — read before `2.4.10 A15.1 Side-Scrolling Platformer`.
  - **What you'll learn from it:** `sprite.layer = N` controls draw order — higher numbers render on top of lower numbers; default is `0`; use `100` (or any high number) for HUD/overlay sprites so they always render above world geometry; the camera transform applies to all layers — to make a HUD that doesn't scroll, you need a different technique (out of scope for this module).
  - **Try it:** R2b sketch + a second sprite at the world origin with `hud.layer = 100; hud.image = '/q5play/img/star.png'`. Student walks the player around and observes the star always renders on top.
- **Glossary rows from §Vocabulary:** `Layer`.

## Worked Examples (teacher-led)

### Worked Example 1 — Animate a sprite (10 min)
Use placeholder colored squares as "frames" — students can swap in image URLs later.
```js
let player;

function setup() {
  new Canvas(400, 300);
  player = new Sprite(200, 250, 40, 40);

  // Without real images, use colors as placeholder "frames"
  // Students will later supply image URLs
  player.addAni('idle', 'img/idle.png');
  player.addAni('run',  'img/run1.png', 'img/run2.png');
  player.changeAni('idle');
}

function draw() {
  background('#222');
  if (kb.pressing('right')) {
    player.vel.x = 4;
    player.changeAni('run');
  } else {
    player.vel.x = 0;
    player.changeAni('idle');
  }
}
```

### Worked Example 2 — Camera follow (10 min)
```js
let player, world;

function setup() {
  new Canvas(400, 300);
  world = new Group();  // platforms
  for (let x = 0; x < 2000; x += 200) {
    let platform = new Sprite(x, 280, 150, 10);
    platform.collider = 'static';
    world.push(platform);
  }
  player = new Sprite(100, 200, 30, 30);
  world.gravity.y = 15;
}

function draw() {
  background('#224');
  // Camera follows player horizontally
  camera.x = player.pos.x - canvas.w / 2 + 100;
  // Simple movement
  if (kb.pressing('right')) player.vel.x = 5;
  else if (kb.pressing('left')) player.vel.x = -5;
  else player.vel.x = 0;
}
```

### Worked Example 3 — Smooth camera (5 min)
```js
camera.x = lerp(camera.x, player.pos.x - canvas.w / 2, 0.1);
```
Increase `0.1` → snappier; decrease → laggier. Show the feel difference live.

## Vocabulary

| Term | Definition |
|------|-----------|
| **Animation** | A sequence of frames played in order to create the illusion of motion |
| **Frame (animation)** | One image in the sequence |
| **Active animation** | The animation currently rendering on a sprite (only one at a time) |
| **`frameDelay`** | Game frames per animation frame (higher = slower cycle) |
| **Cycle speed** | How fast an animation advances through its frames |
| **Still art** | A single image rendered with `sprite.image` — no animation cycle |
| **Camera** | The viewport offset — moving it scrolls the view |
| **Viewport** | The visible area of the world rendered to the canvas |
| **World coordinates** | A sprite's absolute `pos.x` / `pos.y` — independent of where the camera is |
| **`camera.x` / `camera.y`** | The center of the viewport in world coordinates |
| **Follow camera** | A camera whose position is updated each frame to track a sprite |
| **Parallax** | Different layers moving at different speeds for depth illusion |
| **`lerp()`** | Linear interpolation — `lerp(a, b, t)` returns a value between a and b |
| **Easing** | Smooth blending of motion via interpolation (e.g. lerp-driven camera) |
| **Layer** | The draw order — higher numbers draw on top |

## Teacher Notes

- Camera math confuses students. The flashlight analogy lands: "The room (world) is dark and full of stuff. Your flashlight (camera) points at one patch at a time."
- `lerp(current, target, t)` with small t (0.05–0.1) gives smooth camera follow that doesn't feel glued.
- Students without image assets can still pass A15.1 using colored sprites — just document the animation-state change clearly in code.
- AP CSP discussion on image representation fits naturally here — sprites are literally pixel grids with RGBA values.
- The atomic animation readings (2.4.3a–d) read fast: each is one short topic + one try-it. The four together still take ~15 minutes — pace accordingly.

### 2.4.3 Reading — Animation overview (parent — trim)

- **Concept:** the mental model — sprites carry a library of named animations; one is active at a time; state-driven games swap between them.
- **Source:** trim existing `lessons/2-4-3-reading-animation/content.md` to **only** the mental-model topic. Move the per-API content (addAni, changeAni, frameDelay, sprite.image) out to the four sub-letter readings below.
- **Try-it shape:** one ` ```js live ` block — single sprite with no `addAni` calls; the default rendering. Inline note that the four sub-letter readings replace this default with the animation system.
- **Pass criterion:** N/A.

### 2.4.3a Reading — `addAni(name, frames)`

- **Concept:** registering a named animation; first registration also becomes the active animation.
- **Source:** lift the addAni section out of the original `2-4-3-reading-animation/content.md`.
- **Try-it shape:** one ` ```js live ` block — sprite + `player.addAni('idle', '/q5play/img/idle.png')`. Student observes the registered animation rendering instead of the default rectangle.
- **Pass criterion:** N/A.

### 2.4.3b Reading — `changeAni(name)`

- **Concept:** swap active animation between previously registered names.
- **Source:** lift the changeAni section out of the parent.
- **Try-it shape:** ` ```js live ` block — register `'idle'` and `'run'`; in `draw`, `if (kb.pressing('right')) player.changeAni('run'); else player.changeAni('idle')`. Student presses Right and watches the swap.
- **Pass criterion:** N/A.

### 2.4.3c Reading — `frameDelay`

- **Concept:** `sprite.animation.frameDelay = N` controls cycle speed.
- **Source:** lift the frameDelay section out of the parent.
- **Try-it shape:** ` ```js live ` block — running animation with `frameDelay = 4` initially; student edits to `12` to feel the slower cadence.
- **Pass criterion:** N/A.

### 2.4.3d Reading — `sprite.image`

- **Concept:** single-frame still art; mutually exclusive with `addAni` on the same sprite.
- **Source:** lift the sprite.image section out of the parent.
- **Try-it shape:** ` ```js live ` block — static ground sprite with `ground.image = '/q5play/img/ground.png'` and no `addAni` calls.
- **Pass criterion:** N/A.

### 2.4.7 Reading — Camera as transform (parent — trim)

- **Concept:** the camera is a coordinate transform — assigning to it shifts the viewport without moving any sprite.
- **Source:** trim existing `lessons/2-4-7-reading-camera/content.md` to the mental-model topic only. Move per-API content out to sub-letter readings.
- **Try-it shape:** one ` ```js live ` block — five static sprites at known x positions; student edits `camera.x = 400` and observes the view shift without sprite-coord changes.
- **Pass criterion:** N/A.

### 2.4.7a Reading — `camera.x` / `camera.y`

- **Concept:** assigning these moves the viewport center.
- **Source:** lift the camera-x-y section out of the parent.
- **Try-it shape:** ` ```js live ` block — long static row + `camera.x += 1` each frame. Student watches the row scroll past.
- **Pass criterion:** N/A.

### 2.4.7b Reading — Camera-follow pattern

- **Concept:** `camera.x = player.pos.x` (or with offset) inside `draw()` makes the view track the player.
- **Source:** lift the follow section out of the parent.
- **Try-it shape:** ` ```js live ` block — player + static row + `camera.x = player.pos.x` each frame. Student walks right and sees the world scroll while the player stays centered.
- **Pass criterion:** N/A.

### 2.4.7c Reading — Smoothing with `lerp`

- **Concept:** `lerp(current, target, t)` replaces hard-set follow with smooth easing.
- **Source:** lift the lerp section out of the parent.
- **Try-it shape:** ` ```js live ` block — replace the R2b hard-follow line with `camera.x = lerp(camera.x, player.pos.x, 0.1)`. Student edits `t` to `0.05`, `0.1`, `0.5` and feels the difference.
- **Pass criterion:** N/A.

### 2.4.7d Reading — `sprite.layer`

- **Concept:** higher layer numbers draw on top — useful for HUD / overlay sprites.
- **Source:** lift the layer section out of the parent.
- **Try-it shape:** ` ```js live ` block — main sprite + a HUD sprite with `hud.layer = 100`. Student walks the player around and observes the HUD always renders on top.
- **Pass criterion:** N/A.
