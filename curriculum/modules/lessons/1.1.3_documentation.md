# Sub-Module 1.1.3 — Documentation and Coding Conventions

> **Book §1.3 · 1 class day · Environment: browser console · Q1 Unit 1.1 Foundations**
> **SLO focus:** SLO 2 primary (structured programming via naming + convention discipline).
> **Granularity bar:** each lesson ships exactly one new concept.

## Context

Book §1.3 is short — just two subsections, naming and variable reuse — but it is the first place the book asks students to judge code quality rather than just correctness. A student who has never thought about *why* `let x = 5;` is worse than `let numberOfStudents = 5;` needs this framed explicitly; the habit doesn't form on its own.

The audience is intro-level, same as the rest of Unit 1.1. Unlike 1.1.2, this section is small enough that the one-concept-per-lesson rule doesn't force much splitting — the book itself only has two ideas.

**Do NOT:**
- Introduce JSDoc as a requirement. It's a later-unit topic (functions haven't been taught yet); if a teacher wants to preview it, that's a live demo, not a graded lesson here.
- Grade the naming/reuse lab harshly. This is students' first exposure to judging their own code quality, not just making it run.
- Confuse this sub-module's narrow book scope (naming + reuse) with the *broader* "documentation and conventions" theme the sub-module title implies. Comments and code layout are real, valuable shCode-authored content carried over here — but they are not book §1.3 content, and the spec says so explicitly at each point.

## Learning Objectives

Students will be able to:

1. Explain why a descriptive variable name is better than a short, vague one.
2. Apply the book's four naming guidelines (human-readable, avoid abbreviations, descriptive-but-concise, agree on terms) to judge a variable name.
3. Write variable names in camelCase.
4. Explain why reusing one variable for unrelated values makes code harder to debug.
5. Rewrite code that reuses a variable so each variable has one clear purpose.
6. Write single-line (`//`) and block (`/* */`) comments.
7. Apply consistent indentation, spacing, and semicolon usage.

## Topics Covered

### Reading content guidance

#### R1 — Naming Variables Well (`1-1-3X-reading-naming-guidelines`)

- **Topic 1: Four guidelines for a good variable name** — read before R2 (camelCase).
  - Use human-readable names (`userName`, not a cryptic abbreviation).
  - Avoid single-letter or bare-abbreviation names except in obvious contexts.
  - Be descriptive but concise — `data` and `value` say nothing; `totalPrice` says everything.
  - Agree on team terms — if the team says "user," don't privately call it "visitor."
  - **Try it:** given a short list of variable names (`x`, `numberOfStudents`, `d`, `currentDay`, `temp`, `bodyTemperature`), log a one-word verdict (good/bad) and a one-sentence reason for each — mirrors book Try It Now 1.3.1.
- **Glossary rows:** `descriptive name`, `coding convention`.

#### R2 — camelCase Naming Style (carry-over, see In-App Lessons)

- **Topic 1: camelCase mechanics** — the syntax convention the book's own examples follow without ever naming it.
- Already present verbatim in the carried-over content; no new authoring needed.
- **Glossary rows (existing):** `camelCase`, `descriptive name` (already covered by R1 — the carried-over glossary can keep its own row without duplication concern; readings don't share a single glossary).

#### R3 — Reuse or Create? (`1-1-3X-reading-variable-reuse`)

- **Topic 1: Why reusing a variable for unrelated values is a bad habit** — single-topic reading, genuinely new (no existing lesson covers this).
  - Reusing one variable (`item`) to hold a number, then a string, then a boolean forces a reader to track what it means at every point in the program.
  - Insight Note: reuse saves a little typing but costs far more in debugging; modern engines optimize extra variables fine, so there's no performance argument for reuse either.
  - **Try it:** show the book's "bad" `item` example (three reassignments, three types) next to its "good" three-separate-variables rewrite, then have the student write their own version of a short reused-variable snippet with separate variables — mirrors book Try It Now 1.3.2.
- **Glossary rows:** `variable reuse`.

#### R4 — Code Layout — Spacing, Indentation, Semicolons (carry-over, see In-App Lessons)

- **Topic 1: 2-space indentation, operator spacing, semicolons** — already present verbatim in the carried-over content.
- **Glossary rows (existing):** `indentation`, `semicolon`, `convention`.

#### R5 — Comments: `//` and `/* */` (carry-over, see In-App Lessons)

## Worked Examples (teacher-led)

### Worked Example 1 — Good vs. Bad Variable Names (10 min)

Book Example 1.3.1. Project two three-line snippets side by side:

```js
// Hard to read
let a = "John";
let b = 90;
let c = a + " scored " + b + "%";
```

```js
// Same logic, better names
let studentName = "John";
let examScore = 90;
let result = studentName + " scored " + examScore + "%";
console.log(result);
```

Ask: what changed about *how the program runs*? (Nothing.) What changed about *how fast you understood it*? (Everything.) That gap is the entire lesson.

## Challenges (optional stretch)

- Take a script you wrote in 1.1.2's labs and rename every variable to be more descriptive, without changing any logic.
- Find a variable-reuse bug in a snippet the teacher provides (a variable that quietly changes type partway through) and rewrite it with separate variables.
- Write a 3-line program on purpose with zero comments, then add a comment above every line — compare how much faster a partner can explain what it does with vs. without comments.

## Vocabulary

| Term | Definition |
|---|---|
| descriptive name | A variable name that clearly communicates what it holds. |
| coding convention | A set of guidelines for writing consistent, readable code. |
| camelCase | Naming style: start lowercase, capitalize each later word (`firstName`). |
| variable reuse | Using the same variable for unrelated values over its lifetime — a bad habit. |
| indentation | Leading whitespace that shows code structure; the class uses 2 spaces. |
| semicolon | The `;` that ends a JavaScript statement. |
| comment | Text in code the computer ignores, written for human readers. |
| block comment | A `/* ... */` comment that can span multiple lines. |
