# Module 1.1.3 — Documentation and Coding Conventions

> **Week 3 · Q1 Console Fundamentals · 3.5 contact hours (2 sessions) · Environment: browser DevTools + in-app editor**
> **SLO focus:** SLO 2 primary (structured programming via conventions). Quiz A3.3 closes the Unit 1.1 unit-level assessment.

## Context

Week 3 formalizes everything Weeks 1–2 did informally. The class coding style guide (see Appendix A of `curriculum-plan.md`) is distributed THIS week and becomes the grading rubric for every code assignment thereafter. Students who finish Week 3 should leave with: a commenting habit, a naming habit, and the knowledge that code is read more often than it is written.

This week also carries the **AP CSP discussion on open source and licensing** — tied-in because JSCAD, FCC, shplay, and countless tools students use are open source.

**Do NOT:**
- Introduce JSDoc as a requirement this week — introduce it as a pattern students will see, practice it properly in W6 Functions.
- Let the style guide become a battle — distribute it, enforce it, move on.
- Grade A3.1 harshly; students are learning to read AND document for the first time.

---

## Learning Objectives

Students will be able to:
1. Write single-line (`//`) and block (`/* */`) comments effectively.
2. Recognize JSDoc-style function documentation (reinforced in W6).
3. Apply consistent indentation (2 spaces), spacing (around operators, after commas), and semicolon usage.
4. Follow naming conventions: camelCase variables/functions, UPPER_SNAKE_CASE constants, PascalCase classes (preview).
5. Write a basic README for a small program.
6. Explain *why* documentation matters — readability for future-you and for teammates.

## Topics Covered
- Single-line comments `//` and block comments `/* */`.
- JSDoc-style function documentation (introduce visually, full practice in W6).
- Indentation (2 spaces), semicolons (required), spacing around operators.
- What a README is and why it exists.
- Code readability as a professional skill.
- The class coding style guide (distribute as 1-page handout; see Appendix A of `curriculum-plan.md`).
- **AP CSP:** Open source and licensing — Creative Commons, MIT License, copyright basics.

## Prerequisites
- Modules 1.1.1 and 1.1.2 complete.
- Student can declare variables, use template literals, and run programs in DevTools or the in-app editor.

## Worked Examples (teacher-led in class)

### Worked Example 1 — "Messy vs clean" side-by-side (15 min)
Project two versions of the same 12-line program side-by-side. Students compare in silence for 60 seconds, then discuss.

**Messy version:**
```js
let a=17;let b="Jordan"
let c=true
console.log(b+" is "+a+" years old")
if(a>=18){console.log("adult")}else{
console.log("minor")}
let x=b.length
console.log(x)
```

**Clean version:**
```js
// Store user info
let userAge = 17;
let userName = "Jordan";
let isStudent = true;

// Check if user is an adult
console.log(`${userName} is ${userAge} years old`);

if (userAge >= 18) {
  console.log("adult");
} else {
  console.log("minor");
}

// Show length of user's name
let nameLength = userName.length;
console.log(`Name has ${nameLength} characters.`);
```

Ask: Which is easier to read? What specifically makes it easier? Collect answers → maps to the style guide bullets.

### Worked Example 2 — JSDoc preview (5 min)
Show (do not require):
```js
/**
 * Calculates total cost including tax.
 * @param {number} price - price before tax in dollars
 * @param {number} taxRate - tax rate as decimal (e.g. 0.0725)
 * @returns {number} total cost in dollars
 */
function totalCost(price, taxRate) {
  return price + (price * taxRate);
}
```
Say: "We'll write these ourselves in Week 6. For now, recognize the pattern — this is how professionals document functions."

### Worked Example 3 — README walkthrough (10 min)
Open a real README on GitHub (JSCAD repo, q5.js repo, or any small library). Walk through the structure:
- Title + 1-sentence what-it-is
- Install / how to run
- Basic usage example
- Link to full docs

Tell students their README for A3.1 is the same 4-section pattern, just smaller (3–5 sentences per section).

## Challenges (optional stretch)

- **Challenge 1:** Take the messy version from Worked Example 1 and clean it yourself, WITHOUT looking at the clean version. Compare afterward.
- **Challenge 2:** Find 3 README files on GitHub that you think are well-written. Copy a link to each + 1 sentence on what makes it good. (Stretch AP CSP connection to open source.)
- **Challenge 3 (AP CSP bonus):** Research one open-source license (MIT, GPL, Apache, Creative Commons) and summarize in 3 sentences: what it lets you do, what it doesn't, and one famous project that uses it.

## Assignments

### A3.1 — Document a Messy Program
**SLO 2 primary (apply coding conventions)**

| | |
|---|---|
| Type | Lab |
| Points | 15 |
| Est. time | 45 min |
| Due | End of Session 2 |

**Task:** Given a 10–15 line messy program, fix formatting, add inline comments explaining every line, write a 3-sentence README.

**Starter file** (teacher distributes):
```js
let p=29.99
let t=0.0725
let n="USB Cable"
let q=3
let s=p*q
let tax=s*t
let total=s+tax
console.log(n+" qty "+q+" subtotal $"+s.toFixed(2))
console.log("tax $"+tax.toFixed(2)+" total $"+total.toFixed(2))
let onSale=true
if(onSale){console.log("ON SALE!")}
```

**Deliverables:**
1. Rewritten `.js` file with:
   - camelCase names (`p` → `unitPrice`, etc.)
   - 2-space indentation
   - Semicolons on every statement
   - An inline `//` comment above (or on) every line
   - Spaces around operators and after commas
   - Template literals instead of `+` concat
2. A `README.md` with:
   - **What it does** (1–2 sentences)
   - **How to run it** (1 sentence — "paste into DevTools console, press Enter")
   - **Example output** (3–4 lines copied from the actual output)

**Rubric (15 pts):**
| Criterion | Pts |
|-----------|-----|
| All variable names renamed to camelCase + descriptive | 3 |
| Consistent 2-space indentation, semicolons, operator spacing | 3 |
| Every line has an explanatory `//` comment | 3 |
| Template literals replace `+` concatenation | 2 |
| README present with all 3 required sections | 3 |
| Program still runs correctly after refactor | 1 |

## Vocabulary

| Term | Definition |
|------|-----------|
| **Comment** | Text in code that the computer ignores, used to explain intent |
| **Single-line comment** | `// ...` — from `//` to end of line |
| **Block comment** | `/* ... */` — spans multiple lines |
| **JSDoc** | A structured comment above a function documenting parameters + return value |
| **README** | A markdown file describing what a project is and how to use it |
| **Indentation** | Leading whitespace that shows code structure (nesting) |
| **Style guide** | A document defining how code should be formatted in a project/team |
| **Convention** | An agreed-upon habit (not a rule the language enforces) |
| **Open source** | Code whose source is freely available, often under a permissive license |
| **License (software)** | A legal statement telling you what you can do with someone's code |

## Teacher Notes

- **Distribute the style guide THIS WEEK.** After this, every lab is graded against it — students need time to internalize before grading gets strict.
- **A3.1 grading should be encouraging.** First exposure to conventions; a student who catches 80% of the violations but misses 20% is doing well.
- **JSDoc is a preview only.** Full practice in Week 6 Functions. Don't penalize missing JSDoc in A3.1.
- **Open-source discussion connects forward.** JSCAD is open source (W19+). shplay is open source (W10+). freeCodeCamp materials have specific licenses. Mention briefly.
- **If students protest "my code works, why does style matter?"** — show them a random W2 submission from the class, ask the author to read it aloud. The pause while they re-read tells the story.
- **A3.3 quiz is the unit-level closure.** Weight accordingly in the gradebook; if a student scores <60%, flag for intervention before W4 Conditionals.
- **Catch up time:** If W1–W2 students fell behind, pair them with strong partners for Activity 4 (Two Towers + Comments) — rewriting comments is a gentle review of syntax.
