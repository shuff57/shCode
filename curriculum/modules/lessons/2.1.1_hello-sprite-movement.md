# Module 2.1.1 — Hello Sprite and Movement

> **Week 10 · Q2 q5play Foundations · 3.5 contact hours (2 sessions) · Environment: q5play in-app editor**
> **SLO focus:** Reinforces SLO 3. First week students use the in-app q5play editor after a quarter of console.
> **Granularity:** Intro-level — each lesson introduces exactly one new concept. See `sub-module-spec-conventions.md` §2a.

## Context

First week of Q2. Students arrive with strong console-JS foundations and low visual-programming exposure. This module is deliberately about the "wow moment" — get a controllable sprite on screen by end of Session 1. The conceptual lift is understanding the **frame loop**: `setup()` runs once, `draw()` runs every frame at ~60 fps. Once students internalize that, everything else in Q2 builds on it.

**Audience:** introductory high-school CS students seeing a graphics/game-loop runtime for the first time. Per `sub-module-spec-conventions.md` §2a, each Numbered Lesson List slot owns exactly one atomic concept — e.g. `new Canvas(...)` is its own reading separate from `new Sprite(...)`, which is separate from `background(color)`. The original `2.1.3 Reading — Canvas & Sprite` bundled seven atomic concepts and was the most common student-stuck-point in W10; this spec splits it into six sub-letter rows (`2.1.3a` through `2.1.3f`) plus one paired practice lab. Six inserts under one integer slot is at the §4.1 recommended ceiling and reflects a retroactive granularity pass on shipped content; future units author atomic from the start.

**Do NOT:**
- Explain classes yet (`new Sprite()` is used without explanation — deliberate setup for W12).
- Allow complex physics discussions (gravity, bounciness come next week).
- Let students set `vel.x = 50` — they'll launch sprites off-screen. Enforce "small numbers, 2–6 is plenty."
- Bundle Canvas, Sprite, the variable-binding rule, `background()`, and the sprite property tour into a single "intro reading." That's the bundling that triggered this granularity pass; don't recreate it.

## Learning Objectives

Students will be able to:
1. Distinguish `setup()` (once) from `draw()` (every frame) and predict which runs when.
2. Open a drawing area with `new Canvas(w, h)` and locate `(0, 0)` (top-left, y increases downward).
3. Create a rectangle with `new Sprite(x, y, w, h)` and set its `.color`.
4. Store a sprite in a `let` variable assigned inside `setup()`, and explain why creating sprites inside `draw()` causes pile-up.
5. Place `background(color)` as the first call inside `draw()` and predict what happens if it's omitted once motion exists.
6. Read and write the basic sprite properties `pos`, `rotation`, and `layer`.
7. Explain the frame loop: `draw()` runs ~60 times per second.
8. Recognize that `vel` is an additional sprite property whose role is deferred to 2.1.7a (no behavior asked for yet).

## Topics Covered

Each bullet maps 1:1 to a Numbered Lesson List slot in §16.

**Frame-loop schedule**
- The engine calls `setup()` once at start and `draw()` every frame at ~60 fps. (→ 2.1.3)

**Canvas**
- `new Canvas(w, h)` opens a drawing area; `(0, 0)` is top-left; y increases downward. (→ 2.1.3a)

**Sprite**
- `new Sprite(x, y, w, h)` creates a rectangle the engine draws automatically; `.color` sets its fill. (→ 2.1.3b)
- *Practice in isolation:* drop a sprite, change its color. (→ 2.1.3c lab)

**Sprite as a variable**
- Storing the sprite in a `let` declared at file scope and assigned in `setup()`; why creating sprites inside `draw()` is wrong. (→ 2.1.3d)

**Background wipe**
- `background(color)` must be the first call in `draw()` to clear the previous frame. (→ 2.1.3e)

**Sprite property tour**
- Reading and writing `pos`, `rotation`, `layer`. (`vel` is deliberately excluded; it owns its own slot in §2.1.7a.) (→ 2.1.3f)

## Worked Examples (teacher-led in class)

### Worked Example 1 — Minimum sprite program (10 min, Session 1)
Type live on the projector. Type EVERY character; no copy-paste.
```js
function setup() {
  new Canvas(400, 400);
}

function draw() {
  background('#222');
  new Sprite(200, 200, 40, 40);
}
```
Run. Point at the gray canvas and the square. Ask: "What if I wanted the sprite to stay the same each frame instead of getting redrawn?" → student aha → hoist the sprite out of `draw()`.

Evolve the code live:
```js
let player;

function setup() {
  new Canvas(400, 400);
  player = new Sprite(200, 200, 40, 40);
  player.color = 'deepskyblue';
}

function draw() {
  background('#222');
}
```
Physics engine draws `player` automatically — no explicit render call.

### Worked Example 2 — Keyboard movement (10 min, Session 2)
Extend the Session 1 code:
```js
function draw() {
  background('#222');
  if (kb.pressing('left'))  player.vel.x = -4;
  else if (kb.pressing('right')) player.vel.x = 4;
  else player.vel.x = 0;
}
```
Run. Hold arrow keys. Show what happens if you OMIT the else branch (sprite drifts forever once released).

## Vocabulary

| Term | Definition |
|------|-----------|
| **Canvas** | The drawing area set up by `new Canvas(w, h)` |
| **Sprite** | A q5play object representing a visual, physics-aware entity |
| **Frame** | One iteration of the `draw()` loop — happens ~60 times per second |
| **Velocity (`vel`)** | Speed in pixels per frame; `vel.x = 4` = move right 4 px each frame |
| **Frame rate** | Frames per second (fps); q5play targets 60 |
| **Level-triggered input** | `kb.pressing(k)` — true *while* key is held |

---

## Teacher Notes

- `vel.x`/`vel.y` are **pixels per frame**. At 60 fps, `vel.x = 4` = 240 px/s. Students who pick `50` will launch sprites off-screen instantly. Enforce "2–6 is plenty."
- Omitting `vel.x = 0` in the else branch is the #1 bug this week. Watch for it.
- Some students will try `player.x = ...` — show that `player.pos.x` works, but `vel` is the idiom for controlled motion.
- Do NOT explain `new` or classes yet. Students can type `new Sprite(...)` by muscle memory — that's perfect setup for W12.
- The arrow keys scroll the editor iframe on some platforms. Recommend WASD as the default control scheme for all labs.

### 2.1.3b Reading — Sprite

- **Concept:** `new Sprite(x, y, w, h)` creates a rectangle the engine renders automatically; `.color` sets its fill.
- **Source:** lift "`new Sprite(x, y, width, height)` makes a rectangle the engine draws for you" — minus the y-axis-down callout (moved to 2.1.3a) and minus the variable-binding subsection (moved to 2.1.3d).
- **Try-it shape:** two ` ```js live ` blocks. **Block 1** — `new Canvas(...)` + `new Sprite(180, 180, 60, 60)` (no `.color` set, no file-scope variable) + `draw()` calling `background('#222')`. Shows the default-colored sprite. **Block 2** — same shape, but the construction line is `new Sprite(180, 180, 60, 60).color = 'tomato';` — a *chained expression* that creates the sprite and sets its color in one statement. **Critical:** do NOT use `let player; player = new Sprite(...);` here — that pattern is reserved for `2.1.3d` (variable-binding). The chained-expression form demonstrates `.color` without smuggling the variable-binding rule one lesson early. Add a one-line "heads-up" at the bottom telling the student that `2.1.3d` will introduce the `let` form, which is more flexible because you can change the color later.
- **Glossary rows:** Sprite, `new Sprite(x, y, w, h)`, `.color`, centre position.
- **Pass criterion:** N/A.

### 2.1.3c Lab — Drop one sprite, change its color (paired practice)

- **Concept:** practice 2.1.3b in isolation — write the canvas + sprite + color lines from scratch.
- **Starter shape:** scaffolded `script.js` per `q5play-lesson-conventions.md`. ### 2.1.3e Reading — `background(color)` wipe rule

- **Concept:** `background(color)` must be the first line inside `draw()` to clear the previous frame; without it, motion paints trails.
- **Source:** lift "`background(color)` must be the first line of `draw()`" from the parent reading.
- **Try-it shape:** one ` ```js live ` block. Sprite created in `setup()` with a `let` variable (taught in the *previous* reading 2.1.3d, so the binding is fair game here). Inside `draw()`, `background('#222')` is **commented out**, and a single motion line `player.pos.x = player.pos.x + 1;` increments the sprite's position each frame. Trails appear. Student uncomments `background()` and the trails vanish. The motion line uses `pos.x` (formally introduced in the *next* reading 2.1.3f) — frame this as a one-line forward reference inline ("you'll meet `pos.x` properly in 2.1.3f"), not as a new concept this reading owns. - **Glossary rows:** `background(color)`, wipe, frame trail, CSS color string.
