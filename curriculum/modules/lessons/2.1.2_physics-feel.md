# Module 2.1.2 — Physics Feel

> **Week 11 · Q2 q5play Foundations · 3.5 contact hours · Environment: q5play in-app editor**
> **SLO focus:** Reinforces SLO 3. Introduces physics concepts (gravity, bounciness, friction) via q5play's Box2D wrapper.

## Context

Week 11 is where the physics engine stops being invisible. Students enable gravity, tune bounciness, and see how `static` / `dynamic` / `kinematic` sprite bodies behave differently. The single most important takeaway: **the engine drives motion; students supply forces or velocities — not direct position updates**. Students who assign `player.pos.x = ...` every frame fight the physics engine and get jittery results.

**Do NOT:**
- Introduce joints or constraints (those land in W17).
- Go deep on Box2D internals — stick to `world.gravity`, `bounciness`, `friction`, body types.
- Let students set `bounciness = 1` and expect perpetual motion — address the energy-loss question head-on.

---

## Learning Objectives

Students will be able to:
1. Enable/disable gravity with `world.gravity.y`.
2. Set `bounciness` (restitution) and `friction` on sprites and predict effects.
3. Distinguish **dynamic**, **static**, and **kinematic** sprite bodies and choose appropriately.
4. Predict sprite motion given initial velocity + gravity.
5. Debug physics behavior by adjusting one property at a time.
6. Explain why assigning `vel` every frame "fights" the engine (vs using `applyForce`).

## Topics Covered
- `world.gravity` — global physics setting (y = positive downward).
- Sprite body types: `dynamic` (affected by forces), `static` (immovable), `kinematic` (moves but ignores forces).
- `sprite.bounciness` / restitution (0 = dead stop, 1 = lossless bounce).
- `sprite.friction` and `sprite.drag` (air resistance).
- Forces vs velocity: `applyForce(fx, fy)` vs assigning `vel`.
- Automatic collision response — no collision-detection code needed this week.

## Worked Examples (teacher-led)

### Worked Example 1 — Enable gravity (5 min)
Start from 2.1.1's controllable sprite. Add one line:
```js
function setup() {
  new Canvas(400, 400);
  world.gravity.y = 10;      // ← NEW
  player = new Sprite(200, 100, 40, 40);
  player.color = 'deepskyblue';
}
```
Run. Sprite falls. Note: `y` increases downward.

### Worked Example 2 — Static floor + bouncy ball (10 min)
```js
let ball, floor;

function setup() {
  new Canvas(400, 400);
  world.gravity.y = 10;

  ball = new Sprite(200, 50, 30, 30);
  ball.color = 'hotpink';
  ball.bounciness = 0.8;

  floor = new Sprite(200, 380, 400, 20);
  floor.color = 'slategray';
  floor.collider = 'static';
}

function draw() {
  background('#222');
}
```
Run. Ball bounces, loses energy, eventually rests. Show what happens if you change `bounciness` to `1.0` (nearly lossless) or `0.1` (dead thud).

### Worked Example 3 — Body types compared (5 min)
Add three more sprites to the scene, each a different body type. Push/touch them interactively to show behavior differences. Key takeaway table:

| Body type | Affected by forces? | Moves? | Typical use |
|-----------|---------------------|--------|-------------|
| `dynamic` | yes | yes | Player, enemies, projectiles |
| `static` | no | no | Walls, floors, immovable obstacles |
| `kinematic` | no | yes (you move it) | Moving platforms, elevators |

## Challenges (optional stretch)

- **Challenge 1:** Make the bouncing ball into a "sticky ball" — `bounciness = 0`. Does it slide or stick? Why?
- **Challenge 2:** Create a row of 5 balls each with different `bounciness` values (0, 0.25, 0.5, 0.75, 1.0). Drop them simultaneously. Observe.
- **Challenge 3:** Turn `world.gravity.y` negative. What happens? Explain why some games (space shooters) use this.

### A11.2 — Forces vs Velocity
**Written support**

| | |
|---|---|
| Type | Written |
| Points | 5 |

**Prompt (short paragraph, 100–150 words):**
Why does setting `vel` every single frame "fight" the physics engine? Describe (a) what the engine is trying to do each frame, (b) what happens when your code overrides `vel` every frame, and (c) when you might reasonably assign `vel` directly vs when you should use `applyForce(fx, fy)` instead.

**Rubric (5 pts):**
- 2 pts: accurate description of the engine's per-frame work
- 2 pts: clear explanation of the conflict
- 1 pt: at least one concrete example of each approach's right use

## Vocabulary

| Term | Definition |
|------|-----------|
| **Gravity** | Acceleration applied to dynamic sprites each frame (`world.gravity`) |
| **Bounciness** (restitution) | How much of a sprite's velocity is preserved after a collision (0 = none, 1 = all) |
| **Friction** | How much motion is lost when sprites slide against each other |
| **Dynamic body** | A sprite that responds to forces and collisions |
| **Static body** | A sprite that never moves, regardless of forces |
| **Kinematic body** | A sprite you move manually; unaffected by forces |
| **`applyForce(fx, fy)`** | Add an impulse to a sprite — the engine integrates it into motion |

---

## Teacher Notes

- `bounciness = 1` looks perpetual but isn't — air drag and contact jitter still bleed energy. Explain this proactively.
- Setting `vel` directly every frame is fine for player input (see W10); it becomes a problem when you want realistic projectile motion. `applyForce` is right for gunshots, jumps, explosions.
- The pendulum worked example (`q5play-pendulum`) is reserved for W14 — don't front-load.
- Keep the Box2D reference link as "for the curious"; don't make students read it.
