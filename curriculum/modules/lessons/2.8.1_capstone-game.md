# Module 2.8.1 — Capstone Game (Synthesis)

> **Q2 Capstone · 3.5 contact hours in class + homework · Environment: q5play in-app editor**
> **SLO focus: PRIMARY Semester 1 evidence for SLO 3 (design/implement/test). Contributes to SLO 1 (lived SDLC) and SLO 2 (classes + state machines in a shipped product).**
>
> **Renumber note:** Was 2.7.1 before Unit 2.5 was split into 2.5 (Game Saves) + 2.6 (Game States). Cascaded to 2.8.1.

## Context

This unit is entirely capstone. No new content. Students ship a complete game they designed, write a testing log, and deliver a 3-minute showcase. The A18.1 capstone is **the primary SLO 3 artifact for Semester 1** — teacher retains design docs, testing logs, and reflections in the dual-enrollment evidence binder. The Semester 1 Final Exam is scheduled alongside this unit on a separate day.

Grade weight: A18.1 counts as 15% of the course total (single largest graded item in Q2).

**Do NOT:**
- Introduce new content in this unit — if a student hasn't mastered something, route them to it via reference material, not new lecture.
- Grade the capstone on polish alone — the testing log + reflection are equally important for SLO evidence.
- Skip the showcase — presentation is part of the grade.

---

## Learning Objectives

Students will:
1. Design a complete game specification independently.
2. Implement the design using q5play patterns from Units 2.1–2.7.
3. Run and document manual test cases on key logic.
4. Document the design, code, and development reflection.
5. Iterate based on peer and teacher feedback.
6. Present a 3-minute showcase to the class.

## Topics
- Design-doc structure: premise, mechanics, controls, states, win condition, stretch goals.
- Time management across a multi-day build.
- Version control habits: commit frequency + message quality.
- Playtesting as testing.

## Worked Examples

### Worked Example 1 — Scope negotiation (10 min, Monday)
Teacher walks through 3 hypothetical design docs:
1. "Open-world RPG with 20 classes and 100 NPCs" → **too big**, negotiate down
2. "A character that moves left and right" → **too small**, push for stretch
3. "Platformer with 3 levels, enemies, a boss, and a score" → **right-sized** — maybe the boss is a stretch goal

Teach scope vocabulary: **must-have** vs **stretch goal**.

### Worked Example 2 — Writing a testing log (10 min, Wednesday)
Show on projector a template:
```
Test 1: Player can jump when on ground
  Expected: pressing space makes player move up
  Actual: works
  Pass: ✓

Test 2: Player cannot double-jump
  Expected: pressing space mid-air does nothing
  Actual: player super-jumps — bug!
  Fix: added `&& player.colliding(ground)` check
  Pass: ✓ (after fix)

Test 3: Score saves on game over
  Expected: reloading page shows previous high score
  Actual: score was 5, after reload shows 5
  Pass: ✓
```
Every capstone must submit a log like this with ≥5 tests.

### Required deliverables

**1. Design doc (1–2 pp)** — drafted at end of Unit 2.7, refined on Day 1 of Unit 2.8. Must include:
- Premise (1–2 sentences)
- Mechanics (bullet list)
- Controls (key-by-key)
- All game states (menu, play, end, optionally pause)
- Win condition
- Lose condition (if applicable)
- At least 2 stretch goals

**2. Implementation** — runnable game in the in-app editor. Required elements:
- **≥ 1 custom class** (SLO 2) — your own class, not just `Sprite`
- **≥ 1 Group** (collections + arrays)
- **Persistent storage** for ≥ 1 piece of data (SLO 3 File I/O) — e.g., high score
- **≥ 3 game states** driven by a switch or if/else chain
- Non-trivial win/lose logic (not "press space to win")
- Code follows the class style guide (W3)

**3. Testing log** — ≥ 5 manual test cases with expected vs actual outcome and fixes applied (see Worked Example 2 template).

**4. Reflection (1 pp)** — walk through the SDLC phases as you lived them: design, code, test, plan for maintenance. Be specific — not "I designed, then I coded." Describe what changed from your original design and why.

**5. Commits** — ≥ 5 meaningful commits across the unit (or equivalent save milestones if the course platform uses its own versioning).

**6. Showcase** — 3-minute demo to the class Friday.

### Rubric (100 pts total)

| Criterion | Pts | What wins full credit |
|-----------|-----|----------------------|
| Design doc (20 pts) | 20 | All required sections, realistic scope, stretch goals stated |
| Implementation (40 pts) | 40 | All required elements, runs without errors, non-trivial logic |
| Testing log (15 pts) | 15 | ≥ 5 tests, at least one caught + fixed a real bug |
| Reflection (15 pts) | 15 | Specific walk through SDLC, at least one concrete "what I'd do differently" |
| Showcase (10 pts) | 10 | 3 min, clear narrative, demos key mechanics, handles Q&A |

### Grading notes for teacher

- **Students who don't finish by Friday** still present what they have. The testing log + reflection can describe what they would fix. **Iteration is a graded step.**
- **Retain all design docs, testing logs, and reflections** — this is the Sem 1 SLO 3 dual-enrollment evidence.
- **AP CSP Discussion (15 min, during build sessions):** Beneficial and harmful effects of computing — games shape player behavior (addictive loops, fair challenge, inclusive design). Build prompt into showcase Q&A: "What ethical choices did you make in your game design?"

## Vocabulary

| Term | Definition |
|------|-----------|
| **Capstone** | The culminating project of a unit/course demonstrating mastery |
| **Scope** | What's in vs out of a project; must be realistic for the time available |
| **Must-have** | A feature that's non-negotiable |
| **Stretch goal** | A feature you'll add if time allows |
| **Testing log** | A written record of tests run: input → expected → actual → fix |
| **Postmortem / Reflection** | A write-up after the project of what went well, what didn't, and why |
| **Showcase** | A time-boxed demo of your work to an audience |
