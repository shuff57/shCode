# Sub-Module 1.1.4 — Programming Paradigms and Languages

> **Book §1.4 · 1 class day · Environment: browser console · Q1 Unit 1.1 Foundations**
> **SLO focus:** SLO 2 primary (structured programming as a named, defined concept).
> **Granularity bar:** each lesson ships exactly one new concept.

## Context

Book §1.4 is the first purely conceptual section in the course — no new syntax, no new console output to predict. It answers two questions students have been quietly wondering since day one: "why does every language look different?" and "what does it mean that code can be organized different ways?" The payoff is vocabulary that recurs for the rest of the year: every time this course points forward to a later unit ("we'll write functional style in Chapter 3," "OOP is Chapter 5"), it's cashing in a term this sub-module defines.

Because this section has almost no code to write, it doesn't fit the console-track's usual "read, then practice by writing a line" rhythm. The book's own check-for-understanding is a multiple-choice "Concepts in Practice" box, not a Try It Now. This sub-module follows that lead — mostly readings, one capstone classification lab rather than several small writing labs.

**Do NOT:**
- Ask students to *write* OOP or functional code. Neither has been taught yet (OOP is a much later unit; functional style is Chapter 3). This section is about recognizing paradigms in code the student reads, not producing them.
- Treat "which language is best" as a real question. The book's own framing — purpose-driven design, not a ranking — is the point of §1.4.1; don't undercut it.
- Skip structured programming's "three structures" claim as filler. It is the direct ancestor of Unit 1.2 (Control Flow) — sequence is what students already do, selection and repetition are literally next.

## Learning Objectives

Students will be able to:

1. Explain why many programming languages exist rather than one, using the "purpose-driven" framing.
2. Distinguish a low-level language from a high-level language and name a trade-off of each.
3. Define "programming paradigm" in their own words.
4. Describe procedural programming and give an example.
5. Name the three structures of structured programming (sequence, selection, repetition) and say what each means.
6. Describe object-oriented programming and what it bundles together.
7. Describe the distinctive habit of functional programming.
8. Explain what it means to call JavaScript "multi-paradigm."
9. Given a short code snippet, identify which paradigm it best represents.

### Reading content guidance

#### R1 — Why So Many Languages (`1-1-4X-reading-why-languages`)

- **Topic 1: Languages are purpose-driven** — single-topic reading.
  - Thousands of languages exist because each is designed for a kind of work, not ranked against the others.
  - The book's own list (JavaScript for the web, Python for data/teaching, C for hardware, SQL for databases, Swift/Kotlin for phone apps) is illustrative, not exhaustive.
  - Insight Note: languages come and go faster than the underlying ideas (variables, conditions, loops, functions) — that's why this course is titled "Programming Concepts," not "JavaScript."
  - **Try it:** no runnable code fits this topic naturally (the book's own check is multiple-choice). Use a short written-response prompt instead: "name one language and the kind of work it was built for, in one sentence."
- **Glossary rows:** purpose driven.

#### R2 — Low-Level and High-Level Languages (`1-1-4X-reading-abstraction-levels`)

- **Topic 1: Level of abstraction** — single-topic reading.
  - A low-level language makes you handle hardware detail directly — fast to run, slow and error-prone to write.
  - A high-level language hides that detail — faster to write, gives up some control and speed.
  - JavaScript is high-level; the two-line `let total = 5 + 3; console.log(total);` example has already been hiding memory/processor detail since §1.2.
  - **Try it:** run the book's own `let total = 5 + 3; console.log(total);` and discuss out loud everything it *doesn't* make you think about (where `5` and `3` live in memory, how the processor adds them, how the text reaches the screen).
- **Glossary rows:** level of abstraction, low-level language, high-level language.

#### R3 — What a Paradigm Is (`1-1-4X-reading-what-is-paradigm`)

- **Topic 1: A paradigm is a style of organizing a program** — single-topic, short reading (book §1.4.3 is brief by design, a hinge between R2 and the three paradigm readings that follow).
  - Two programs can solve the same problem and be organized completely differently.
  - The three paradigms worth knowing now: procedural, object-oriented, functional.
  - This reading previews; R4–R8 each teach one paradigm in full.
  - **Try it:** none — this is a definitional bridge reading. A short "name the three paradigms we're about to cover" recall prompt is enough.
- **Glossary rows:** programming paradigm.

#### R4 — Procedural Programming (`1-1-4X-reading-procedural`)

- **Topic 1: A program as a sequence of steps on separate data** — single-topic reading.
  - Data (variables) and instructions (statements) are kept separate.
  - The book's `price`/`quantity`/`total` example is exactly what students have been writing since 1.1.2 — this reading names the style they're already using.
  - **Try it:** run the book's own 4-line procedural snippet (`let price = 20; let quantity = 3; let total = price * quantity; console.log(...)`) and ask: is this procedural? (Yes — it's the style's textbook shape.)
- **Glossary rows:** procedural programming.

#### R5 — Structured Programming (`1-1-4X-reading-structured`)

- **Topic 1: The three structures — sequence, selection, repetition** — single-topic reading, the meatiest one in this sub-module.
  - Structured programming is procedural programming with a discipline: no arbitrary jumps (`goto`), only sequence/selection/repetition.
  - The strong claim: **any computation** can be expressed with just these three structures.
  - Context Pause: early languages allowed `goto`; giving it up made programs easier to reason about — the first example in the course of a restriction being a feature.
  - Foreshadow Unit 1.2 explicitly: selection is `if`/`switch`, repetition is loops — both arrive next unit.
  - **Try it:** book's own subtotal/tax/total example (Try It Now 1.4.1) — run it, then ask "which of the three structures does this use?" (sequence only — no branching, nothing repeats, since selection/repetition aren't taught yet).
- **Glossary rows:** structured programming, sequence, selection, repetition.

#### R6 — Object-Oriented Programming (`1-1-4X-reading-oop`)

- **Topic 1: Bundling data with the behavior that acts on it** — single-topic reading.
  - OOP organizes a program around objects that bundle **data** (properties) with **behavior** (methods).
  - Callback to §1.2.7: the `{ title: "...", pages: 200 }` object literal already held data; OOP's idea is to put behavior in there too.
  - Table contrast: procedural keeps data and behavior separate; OOP bundles them.
  - Insight Note: this will feel abstract until a program is big enough to be annoying without it — that payoff is a later unit (Chapter 5), not this one.
  - **Try it:** run the book's `book.title` / `book.pages` property-access example (already-familiar object-literal syntax from 1.1.2) — no new syntax, just a new lens on it.
- **Glossary rows:** object-oriented programming.

#### R7 — Functional Programming (`1-1-4X-reading-functional`)

- **Topic 1: Same input, same output, nothing else changes** — single-topic reading, deliberately brief (book itself defers full treatment to Chapter 3, since functions aren't taught yet).
  - A functional program favors producing new data over modifying existing data.
  - Easier to test and reason about, because a function that depends only on its inputs can be understood in isolation.
  - **Try it:** none — no functions exist yet in the student's vocabulary. This reading is pure preview; skip the "Try it" requirement here and say so explicitly (see `reading-conventions.md` §4's "if you can't think of one, the topic probably isn't load-bearing enough" — this is the rare legitimate exception, matched by the book's own equally code-free treatment).
- **Glossary rows:** functional programming.

#### R8 — JavaScript Is Multi-Paradigm (`1-1-4X-reading-multi-paradigm`)

- **Topic 1: JavaScript supports all three styles at once** — capstone reading, single-topic.
  - Some languages commit to one paradigm; JavaScript doesn't.
  - Maps the book's own three-chapter roadmap: procedural (Ch. 1–3), functional (Ch. 3), object-oriented (Ch. 5+).
  - Real programs mix all three in one file — these are choices, not rules.
  - **Try it:** book's own side-by-side comparison — two snippets (`title`/`pages` as separate variables vs. bundled into a `book` object) that print the identical line. Ask which is procedural and which is object-oriented, and what specifically marks the difference (where the data lives relative to the code using it, not "whether an object appears").
- **Glossary rows:** multi-paradigm.

## Assignments

### A4.1 — Identify the Paradigm (lab)

- **Type:** console lab, classification-style (per `lab-assignment-conventions.md` §7.6's closed-answer exception). Primary SLO-2 evidence artifact.
- **Est. time:** 15 min.
- **Task:** the student is shown 4–5 short code snippets (each already covered in the readings above — the procedural `price*quantity` example, the OOP `book.title` example, etc.) and, for each, writes `console.log("procedural")`, `console.log("object-oriented")`, or `console.log("functional")` naming which paradigm it best represents.
- **Requirements:** regex checks for the correct literal string logged for each snippet — a legitimate closed-answer check, not a "grading a student's chosen value" violation, since each snippet has exactly one correct classification.
- **Pass criteria:** all-green Submit gate. Mastery-graded — resubmit until green.

## Vocabulary

| Term | Definition |
|---|---|
| purpose driven | The principle that a language is designed for a kind of work, which is why many exist. |
| level of abstraction | How far a language sits from the hardware; how much machine detail it hides. |
| high-level language | A language that hides hardware detail so the programmer says what should happen, not how. JavaScript is one. |
| programming paradigm | A style of organizing a program — a set of ideas about what a program is made of. |
| procedural programming | Organizing a program as a sequence of instructions acting on separately held data. |
| structured programming | Building programs only from sequence, selection, and repetition, with no arbitrary jumps. |
| sequence, selection, repetition | The three structures: in order; choose a path; do it again. |
| object-oriented programming | Organizing a program around objects that bundle data with the behavior acting on it. |
| functional programming | Organizing a program around functions that always give the same output for the same input. |
| multi-paradigm | A language supporting more than one of these styles. JavaScript supports all three. |
