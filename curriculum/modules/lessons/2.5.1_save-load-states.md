# Module 2.5.1 — Save, Load, and Game States

> **Week 16 · Q2 State and Persistence · 3.5 contact hours (2 sessions) · Environment: q5play in-app editor**
> **SLO focus:** SLO 2 (state machines as structured programming) + SLO 3 (File I/O via persistent storage — **covers the Butte outline File I/O secondary location**).
> **Audience:** introductory CS students — for most, this is first encounter with persistent storage, JSON serialization, AND state machines as a structuring tool. **Granularity bar applies** (`sub-module-spec-conventions.md` §2a): one new concept per lesson.

## Context

Week 16 is the last hard prerequisite for the W18 capstone. Two big ideas:
1. **Persistent storage** — `storeItem` / `getItem` + JSON export. Without this, a game "forgets" every reload.
2. **State machines** — a `gameState` variable driving `draw()` via `switch`. Without this, there's no flow — just one endless gameplay loop.

A16.1 is the **File I/O SLO artifact** — students add persistent high scores to their W15 game and prove persistence by closing the browser and reopening.

**Audience.** Most students are seeing persistent storage, JSON serialization, *and* state machines for the first time. Per the granularity bar, every reading and try-it owns exactly **one** atomic concept; integration happens only inside the worked examples and the two graded labs (A16.1, A16.2). The "switch" reading at 2.5.15 reinforces a syntactic form first introduced in Q1 W4 — students who are rusty get a fresh single-concept page before it's used as the state-dispatch tool at 2.5.16.

**Do NOT:**
- Let students implement state via a giant `if`-chain — push toward `switch` (2.5.15 + 2.5.16 are the dedicated readings).
- Accept `getItem('x') + 1` bugs unchallenged — the type-coercion reading at 2.5.3a is the dedicated antidote; demo the bug live.
- Put `loadJSON` in `setup()` instead of `preload()` — demo the failure mode (2.5.10 is the dedicated reading).
- Compound `storeItem` + JSON serialization + state machines into one lab — that bundling is exactly what the granularity bar exists to prevent.

## Learning Objectives

Students will be able to:
1. Save data persistently with `storeItem(name, value)`.
2. Retrieve saved data with `getItem(name)` and explain that the return value is always a string.
3. Coerce a stored value back to a number using `Number(...)` (or `parseInt(...)`).
4. Remove a single saved value with `removeItem(name)` and wipe storage with `clearStorage()`.
5. Convert an object to a JSON string with `JSON.stringify(obj)`.
6. Convert a JSON string back to an object with `JSON.parse(str)`.
7. Round-trip a structured value through storage (`stringify → storeItem → getItem → parse`).
8. Export an in-memory object to a downloadable JSON file with `save(obj, 'name.json')`.
9. Load JSON from a URL using `loadJSON(url)` inside `preload()` and explain why it must live there.
10. Declare and assign a state variable (`let gameState = 'menu'`) as the single source of truth for game flow.
11. Read a `switch` statement and pick the correct `case` for a given value.
12. Drive `draw()` with `switch (gameState)` so each state owns its render + input logic.
13. Write a transition triggered by **input** (e.g. `kb.presses('space')` → `gameState = 'play'`).
14. Write a transition triggered by a **game condition** (e.g. `score >= 10` → `gameState = 'win'`).
15. Compose three or more states into a working game flow (menu → play → win/lose → menu).

## Topics Covered

Each bullet is a single atomic concept and corresponds 1:1 to a Numbered Lesson List slot (§Numbered Lesson List). Bundling concepts on a single lesson is forbidden under the granularity bar.

**Persistent storage:**
- `storeItem(name, value)` writes to localStorage; `getItem(name)` reads it back.
- `getItem` always returns a **string** — the type-coercion bug.
- `Number(getItem('x'))` (or `parseInt`) is the fix for numeric values.
- `removeItem(name)` deletes one key; `clearStorage()` wipes all.

**JSON serialization:**
- `JSON.stringify(obj)` converts an object → text string.
- `JSON.parse(str)` converts a text string → object.
- Round-trip pattern: `stringify → storeItem → getItem → parse` for storing structured data.
- `save(obj, 'name.json')` triggers a downloadable JSON file.
- `loadJSON(url)` is **async** and MUST live inside `preload()`.

**State machines:**
- The state variable: `let gameState = '...'` as the single source of truth.
- `switch` syntax (general): `case`, `break`, falls through if `break` is forgotten.
- `switch (gameState)` inside `draw()` — each `case` owns its frame logic.
- Input-driven transitions (`kb.presses(...) → gameState = '...'`).
- Condition-driven transitions (score, lives, timer → `gameState = '...'`).
- Multi-state composition: menu → play → win/lose → menu as a closed loop.

### Reading content guidance

Every reading splits into one or two `## <Topic>` subsections per `reading-conventions.md` §3 — each with a `js live` Try-it block — and ends with a glossary table. Per the granularity bar, **most readings own exactly one topic**; multi-topic readings are reserved for the JSON cluster where stringify and parse are mutual inverses and benefit from juxtaposition.

#### R1 — `storeItem` and `getItem` basics (`2-5-3-reading-storage`)

- **`externalLink`:** `/docs/q5play/storage` (the in-app `Storage` chapter).
- **Topic 1: Writing and reading a single value** — read before `2.5.4 Worked Example — High Score with storeItem`.
  - **What you'll learn from it:** `storeItem(name, value)` writes a key/value pair into the browser's localStorage; `getItem(name)` retrieves it; the data survives page reloads (close the tab, come back, it's still there); each "name" is a unique slot in the per-site storage.
  - **Try it:** in `setup()`, `storeItem('lastScore', 42)` then immediately `console.log(getItem('lastScore'))`. Reload the page (don't re-write) — the log should still print `42`. Student edits the stored value and observes it persisting across reloads.
- **Glossary rows from §Vocabulary:** `Persistence`, `localStorage`, `storeItem` / `getItem`.

#### R1a — `getItem` returns a string (`2-5-3a-reading-getitem-string`)

- **`externalLink`:** `/docs/q5play/storage` (the same Storage chapter).
- **Topic 1: Why `getItem('x') + 1` becomes "01"** — read before `2.5.4 Worked Example — High Score with storeItem`.
  - **What you'll learn from it:** every value `getItem` returns is a string — even values written as numbers; the JS `+` operator concatenates when either operand is a string, so `getItem('x') + 1` produces `"01"`, not `1`; `Number(getItem('x'))` (or `parseInt(getItem('x'))`) coerces the string back to a number; this is the single most common storage bug.
  - **Try it:** `storeItem('n', 5)` in `setup`. In `draw`, `console.log(getItem('n') + 1)` once and `console.log(Number(getItem('n')) + 1)` once. Student reads both logs and sees `"51"` vs `6`.
- **Glossary rows from §Vocabulary:** `Type coercion`, `Number(...)`, `parseInt(...)`.

#### R1b — `removeItem` and `clearStorage` (`2-5-3b-reading-cleanup`)

- **`externalLink`:** `/docs/q5play/storage`.
- **Topic 1: Deleting saved data** — read before `2.5.12 A16.1 Persistent High Scores` (the lab requires a clear button).
  - **What you'll learn from it:** `removeItem(name)` deletes a single key; `clearStorage()` wipes everything this site has stored; both are common in test/debug flows; A16.1 requires a "clear" UI affordance so the student can demo persistence + reset live.
  - **Try it:** `storeItem('x', 1)` and `storeItem('y', 2)` in `setup`. In `draw`, on `kb.presses('c')` call `clearStorage()` and `console.log('cleared')`. Student presses C, reloads, and verifies both keys are gone.
- **Glossary rows from §Vocabulary:** `removeItem`, `clearStorage`.

#### R2 — `JSON.stringify(obj)` (`2-5-6-reading-json-stringify`)

- **`externalLink`:** `/docs/q5play/json` (the in-app `JSON` chapter).
- **Topic 1: Object → string** — read before `2.5.7 Reading — JSON.parse`.
  - **What you'll learn from it:** `JSON.stringify(obj)` walks an object's properties and produces a text string in JSON format; numbers, strings, booleans, arrays, and nested objects all serialize cleanly; functions and `undefined` do not (they get dropped); the result is what you'd want to write to disk or paste into a chat.
  - **Try it:** `let player = { name: 'Ada', score: 42 };` then `console.log(JSON.stringify(player));`. Student edits the object's properties and watches the string output update.
- **Glossary rows from §Vocabulary:** `JSON`, `JSON.stringify`.

#### R3 — `JSON.parse(str)` (`2-5-7-reading-json-parse`)

- **`externalLink`:** `/docs/q5play/json`.
- **Topic 1: String → object** — read before `2.5.8 Reading — Storing structured data`.
  - **What you'll learn from it:** `JSON.parse(str)` is the inverse of `stringify` — it walks a JSON-format string and rebuilds the in-memory object; malformed strings throw a `SyntaxError`, so wrap in `try/catch` if the source is untrusted; the parsed result is a *fresh* object — mutating it doesn't affect the string.
  - **Try it:** start with a JSON string literal `let s = '{"name":"Ada","score":42}'`. `let p = JSON.parse(s);` and `console.log(p.score)`. Student edits the string, reloads, and observes parsing failures when commas / quotes are wrong.
- **Glossary rows from §Vocabulary:** `JSON.parse`.

#### R4 — Storing structured data (`2-5-8-reading-store-structured`)

- **`externalLink`:** `/docs/q5play/storage`.
- **Topic 1: The round-trip pattern** — read before `2.5.12 A16.1 Persistent High Scores`.
  - **What you'll learn from it:** localStorage only stores strings, so anything more structured than a single number / short text needs the round-trip `JSON.stringify(obj) → storeItem → getItem → JSON.parse(str) → obj`; the pattern shows up in *every* "save the player's data" flow; forgetting the parse on read gives back a string that looks like an object but isn't (`obj.score` is `undefined`).
  - **Try it:** `let scores = [9, 7, 5];` then `storeItem('top3', JSON.stringify(scores));` in `setup`. Reload to clear in-memory state — keep the `storeItem` call commented out — and read with `let saved = JSON.parse(getItem('top3')); console.log(saved[0]);`. Student adds / reorders entries and sees them survive reload.
- **Glossary rows from §Vocabulary:** `Round-trip`, `Serialize` / `Deserialize`.

#### R5 — `loadJSON` is async (`2-5-10-reading-loadjson-async`)

- **`externalLink`:** `/docs/q5play/file-io`.
- **Topic 1: Why it must live in `preload()`** — read before `2.5.13 Worked Example — Load JSON in preload`.
  - **What you'll learn from it:** `loadJSON(url)` fetches a JSON file over the network — the result isn't ready immediately; q5play's `preload()` function blocks `setup()` until every preload-issued fetch finishes, which is why `loadJSON` calls *must* live inside `preload()`; calling it from `setup()` returns an empty object that gets populated later, and any code that reads it inline breaks.
  - **Try it:** create a tiny `level1.json` (provide a copy in the lesson directory) with `{ "name": "Level 1" }`. In `preload()`, `levelData = loadJSON('level1.json');`. In `setup()`, `console.log(levelData.name);`. Student then *moves* the `loadJSON` call into `setup` and reloads to watch the bug — `console.log(levelData)` will be `{}`, not the loaded object.
- **Glossary rows from §Vocabulary:** `Async`, `preload()`, `loadJSON`.

#### R6 — The state variable (`2-5-15-reading-state-variable`)

- **`externalLink`:** `/docs/q5play/state-machines`.
- **Topic 1: One variable owns the flow** — read before `2.5.16 Reading — switch syntax`.
  - **What you'll learn from it:** a state variable is just a regular `let` declaration whose value is a short string label (`'menu'`, `'play'`, `'win'`); naming it `gameState` is convention; the rule is one variable holds the current state and only that variable decides what `draw()` runs each frame; this beats sprinkled boolean flags (`isPlaying`, `isPaused`, `isWon`) because impossible combinations (`isPlaying && isPaused`) become unrepresentable.
  - **Try it:** `let gameState = 'menu';` outside `setup`. In `draw`, `console.log(gameState)` once. Student manually edits the variable to `'play'` and reloads to verify the log changes.
- **Glossary rows from §Vocabulary:** `State`, `State variable`.

#### R7 — The `switch` statement (`2-5-16-reading-switch-syntax`)

- **`externalLink`:** [MDN — switch](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/switch).
- **Topic 1: `case`, `break`, and the fall-through trap** — read before `2.5.17 Reading — switch in draw()`.
  - **What you'll learn from it:** `switch (value) { case 'a': … break; case 'b': … break; }` picks the case whose `case` literal matches the value via strict equality (`===`); a missing `break` "falls through" into the next case — sometimes intentional, usually a bug; an optional `default:` runs when no case matches; it's a cleaner alternative to a long `if / else if` chain when you're switching on a single value.
  - **Try it:** `let mood = 'happy';` then a `switch (mood)` with `case 'happy'`, `case 'sad'`, `default` — each logging a different message. Student edits `mood` and the log changes; then they delete a `break` and observe fall-through.
- **Glossary rows from §Vocabulary:** `switch`, `case`, `break`, `Fall-through`.

#### R8 — `switch (gameState)` in `draw()` (`2-5-17-reading-switch-dispatch`)

- **`externalLink`:** `/docs/q5play/state-machines`.
- **Topic 1: State dispatch** — read before `2.5.18 Worked Example — Three-state machine`.
  - **What you'll learn from it:** putting `switch (gameState)` at the top of `draw()` turns each `case` into "the frame logic for this state"; only one case runs per frame, so render + input handling for each state lives in its own block; transitions (changing `gameState`) inside a `case` don't take effect until the *next* frame, which keeps things predictable.
  - **Try it:** start from the R6 sketch with `gameState = 'menu'`. Add `switch (gameState) { case 'menu': background('#222'); text('MENU', 100, 200); break; case 'play': background('#234'); text('PLAY', 100, 200); break; }` to `draw`. Student edits `gameState` and watches the rendered output flip between states.
- **Glossary rows from §Vocabulary:** `State dispatch`, `Frame logic`.

#### R9 — Input-driven transitions (`2-5-19-reading-transitions-input`)

- **`externalLink`:** `/docs/q5play/state-machines`.
- **Topic 1: Press → state change** — read before `2.5.20 A16.2 Game States`.
  - **What you'll learn from it:** the simplest transition is `if (kb.presses('space')) gameState = 'play';` placed *inside* the relevant `case`; using `kb.presses` (one-shot) instead of `kb.pressing` (held) prevents the state from flipping every frame the key is held; transitions belong inside the `case` whose state owns them — `'menu' → 'play'` is logic for `case 'menu'`.
  - **Try it:** start from the R8 sketch. Inside `case 'menu'` add `if (kb.presses(' ')) gameState = 'play';`. Inside `case 'play'` add `if (kb.presses('Escape')) gameState = 'menu';`. Student presses Space and Escape to see the flip.
- **Glossary rows from §Vocabulary:** `Transition`, `One-shot input`.

#### R10 — Condition-driven transitions (`2-5-20-reading-transitions-condition`)

- **`externalLink`:** `/docs/q5play/state-machines`.
- **Topic 1: Game outcome → state change** — read before `2.5.21 A16.2 Game States`.
  - **What you'll learn from it:** transitions don't have to come from input — `if (score >= 10) gameState = 'win';` or `if (lives === 0) gameState = 'lose';` are equally valid; the rule is the same as input-driven (transition lives inside the `case` whose state owns it); be careful not to flip every frame: once `score >= 10`, the next frame is also `>= 10`, so guard the transition or rely on the new `case` not testing the same condition.
  - **Try it:** start from the R9 sketch. Add a `let score = 0;` outside `setup`. Inside `case 'play'` add `score++; if (score >= 60) gameState = 'win';` and a new `case 'win'` that logs once + waits for any keypress to return to menu. Student reloads, presses Space, and watches the auto-transition fire after ~1 second.
- **Glossary rows from §Vocabulary:** `Win condition`, `Guard`.

## Worked Examples (teacher-led)

### Worked Example 1 — High score with `storeItem` (10 min)

```js
let score, highScore;

function setup() {
  new Canvas(400, 400);
  score = 0;
  // Read saved high score, coerce string → number
  highScore = Number(getItem('highScore')) || 0;
}

function draw() {
  background('#222');
  text(`Score: ${score}`, 10, 20);
  text(`Best: ${highScore}`, 10, 40);

  if (score > highScore) {
    highScore = score;
    storeItem('highScore', highScore);
  }
}
```
Run, rack up a score, reload the page — the high score persists. Clear with `clearStorage()` from the DevTools console to reset.

### Worked Example 2 — Export level as JSON (8 min)

```js
let level = {
  name: "Level 1",
  platforms: [
    { x: 100, y: 300, w: 200, h: 20 },
    { x: 400, y: 250, w: 100, h: 20 }
  ],
  enemyCount: 5,
  startPos: { x: 50, y: 100 }
};

function draw() {
  background('#222');
  text('Press E to export level', 10, 20);
  if (kb.presses('e')) save(level, 'level1.json');  // triggers download
}
```

### Worked Example 3 — Load JSON in `preload` (5 min)

```js
let levelData;

function preload() {
  levelData = loadJSON('level1.json');  // async — MUST be in preload
}

function setup() {
  new Canvas(400, 400);
  console.log(levelData.name);  // ready here because preload completes first
}
```
**Demo the bug** by moving `loadJSON` into `setup()` — `levelData.name` is now `undefined`.

### Worked Example 4 — Three-state machine (15 min)

```js
let gameState = 'menu';
let score = 0;

function draw() {
  background('#222');

  switch (gameState) {
    case 'menu':
      text('Press SPACE to start', 100, 200);
      if (kb.presses(' ')) gameState = 'play';
      break;

    case 'play':
      score++;
      text(`Score: ${score}`, 10, 20);
      if (score >= 60) gameState = 'win';
      if (kb.presses('p')) gameState = 'pause';
      break;

    case 'pause':
      text('PAUSED — press P to continue', 90, 200);
      if (kb.presses('p')) gameState = 'play';
      break;

    case 'win':
      text('YOU WIN — press R to restart', 80, 200);
      if (kb.presses('r')) { score = 0; gameState = 'menu'; }
      break;
  }
}
```
Point out: one variable drives the entire flow. Transitions live inside their own cases.

| Has an input-driven transition (menu → play) | `kb.presses(...)` followed within ~200 chars by `gameState = ` inside a `case 'menu'` body |
| Has a condition-driven end transition (play → win/lose) | `gameState = 'win'` OR `gameState = 'lose'` inside `case 'play'` |
| Has a return-to-menu transition | `gameState = 'menu'` inside any non-`'menu'` case |

## Vocabulary

| Term | Definition |
|------|-----------|
| **Persistence** | Data that survives a page reload |
| **localStorage** | Browser-provided key/value store (~5 MB) |
| **`storeItem` / `getItem`** | q5play wrappers around localStorage |
| **`removeItem`** | Delete a single saved key |
| **`clearStorage`** | Wipe everything this site has stored |
| **Type coercion** | Forcing a value into a different type (`Number(...)`, `parseInt(...)`) |
| **`Number(...)`** | Coerces its argument to a JS number — `Number("42")` is `42` |
| **`parseInt(...)`** | Coerces its argument to an integer, parsing leading digits |
| **JSON** | JavaScript Object Notation — a text format for structured data |
| **`JSON.stringify`** | Convert object → JSON string |
| **`JSON.parse`** | Convert JSON string → object |
| **Round-trip** | Send a value through serialize → store → retrieve → deserialize and get back an equivalent value |
| **Serialize** / **Deserialize** | Convert a value to/from a transport format (here: JSON text) |
| **Async** | Code whose result isn't ready immediately (`loadJSON` over the network) |
| **`preload()`** | q5play function that runs before `setup()`; the only correct home for `loadJSON` |
| **`loadJSON`** | Fetches a JSON file from a URL (async) |
| **State** | A label that describes "what the game is currently doing" |
| **State variable** | The single `let` whose value is the current state — e.g. `gameState` |
| **State dispatch** | Picking the per-state frame logic from a single value (typically via `switch`) |
| **`switch`** | JS statement that dispatches on a value's strict equality to literal `case` labels |
| **`case`** | One labeled branch inside a `switch` |
| **`break`** | Exits the current `switch` block — required between cases unless intentional fall-through |
| **Fall-through** | What happens when a `case` is missing its `break` and execution flows into the next `case` |
| **Frame logic** | The work `draw()` does for one frame in one specific state |
| **Transition** | A line that assigns a new value to the state variable — moves the game from one state to another |
| **One-shot input** | `kb.presses(...)` (true on the frame the key is first pressed), as opposed to `kb.pressing(...)` (true every frame the key is held) |
| **Win condition** | A boolean expression that, when true, transitions the game to a `'win'` state |
| **Guard** | An extra condition that prevents a transition from re-firing every frame |

## Teacher Notes

- **The string-return bug is the one to demo live.** `console.log(getItem('x') + 1)` next to `console.log(Number(getItem('x')) + 1)` is the cleanest way to make the type-coercion concept stick. The reading at 2.5.3a is the dedicated written version, but the live demo is the one students remember.
- **`loadJSON` async demo.** Move the `loadJSON` call from `preload()` into `setup()` and reload — the `console.log` then prints `{}` instead of the loaded object. That live failure is the lesson; don't try to explain it abstractly first.
- **State machines vs `if`-chains.** Many students default to `if (gameState === 'menu') { … } else if (gameState === 'play') { … }`. Redirect to `switch` for readability — easier to add a state later, and a missing `case` is more visible than a missing `else if`.
- **A16.1 is the SLO-3 evidence artifact.** The Butte outline File I/O secondary location is satisfied by persistent storage + JSON serialization — A16.1 is non-negotiable for SLO-3 coverage. A16.2 covers SLO-2 (structured programming via state machines).
- **This module is a hard prerequisite for the W18 capstone.** The capstone rubric expects persistent storage AND multi-state flow. Do not let students skip 2.5.

### 2.5.3 Reading — storeItem and getItem
- **Single concept:** writing and reading one key/value pair via `storeItem(name, value)` + `getItem(name)`.
- **Try-it shape:** `storeItem('lastScore', 42)` in `setup`; `console.log(getItem('lastScore'))` once. Reload demonstrates persistence.
