# Module 5.2: Physics Feel

**Quarter 2 · ~2.3 contact hours (one long class meeting, or two short ones; 35 minutes of that is the random-numbers-and-timers opener, 5.2.1–5.2.4)**
**Environment:** moSHion in-app editor (built on q5.js + Box2D physics).

## Context

§5.1 gave students a sprite that moves because they set `.vel` directly, every frame,
themselves. §5.2 hands the same scene to a physics engine and asks students to tune it
instead of drive it: gravity, bounciness, friction, and `applyForce` are all dials, and
—per the book's own Context Pause—the section's real subject is what turning each dial
does to how the game *feels*, not a single correct value. That framing should carry into
every lesson here: labs ask students to try several values and describe the difference,
not to hit one target number.

The section also does double duty as the last stop before OOP (Module 7.1 next): the finished
player/ground/goal/wall scene built lesson-by-lesson through §5.2.1–§5.2.6 is exactly the
program Module 7.2 later refactors into a `Goal` class. Nothing here should pre-empt that
refactor — the win condition stays a loose `goal` variable and a manual distance check,
even though it's clunky, because the clunkiness is what makes Module 7.2's class version land.

**Only one lesson currently exists for this module**, `moshion-bounce` (title `5.2.5
Bouncy Ball`), and it was orphaned until 2026-08-16: no `id: "5.2"` module file existed,
so it rendered on no `/module` page and was reachable only by direct URL. This spec
folds it back in as a carry-over (§ In-App Lessons below) and designs the other 14
lesson slots around it.

**Do NOT:**
- Explain `kinematic` bodies. The book never defines the term (only `dynamic`, the
  default, and `static`, used for `ground`/walls) — teaching a third body type here adds
  vocabulary the book and the graded work never test. Treat "dynamic vs static" as the
  actual pair; if `kinematic` comes up, it's a vocabulary aside, not a lesson slot.
- Let a lab reward one "correct" gravity/bounciness/friction value. The grader can check
  that a property was *set*, never that it was set to the *right* feeling — that judgment
  is what the written assignment (A5.2.2) and in-class discussion are for.
- Pre-empt Module 7.2 by wrapping the goal in a class, a function that returns early, or any
  other cleanup. The manual, slightly repetitive version is the point.

## Learning Objectives

Students will be able to:
1. Set `world.gravity.y` and predict its effect (falls, floats, drifts up) on a dynamic sprite.
2. Distinguish a `dynamic` sprite (default; affected by gravity/forces) from a `static` one (immovable; used for ground/walls).
3. Gate an action on a physics condition using `sprite.colliding(otherSprite)`.
4. Explain why `kb.presses(...)` (edge-triggered) is the right choice for a jump, where `kb.pressing(...)` (level-triggered, from §5.1) is not.
5. Set `.bounciness` and `.friction` on a sprite and predict the qualitative effect of low vs. high values.
6. State the two-sprite combining rule: bounciness uses the higher value, friction uses a geometric mean.
7. Call `sprite.applyForce(fx, fy)` and explain how it differs from setting `.vel` directly (units, mass, additive vs. overriding).
8. Call `sprite.delete()` and explain why it's different from `sprite.visible = false`.
9. Write a single-fire event check (a condition guarded so its side effect happens exactly once, not every frame it stays true).
10. Say when moSHion runs `update()` (every frame, before the physics step) and `draw()` (after it), and move a sketch's keys and movement into `update()` while `draw()` keeps the picture.

## Topics Covered

*Gravity*
- `world.gravity.y`: sets vertical gravity for every dynamic sprite; positive down, `0` off, negative up
- `dynamic` vs `static` sprite bodies

*Ground-gated actions*
- `sprite.colliding(otherSprite)`: true while two sprites touch
- `kb.presses(key)` (edge-triggered, fires once per press) vs `kb.pressing(key)` (level-triggered, §5.1)
- Combining a key-press with a ground check to gate a jump

*Bounciness and friction*
- `.bounciness` (restitution): 0 sticks, 1 bounces at full speed
- `.friction`: 0 is ice, higher drags motion to a stop
- Two-sprite combining rule: bounciness uses the max, friction uses a geometric mean

*Forces*
- `sprite.applyForce(fx, fy)`: Newtons, respects mass, adds to existing motion
- `.vel` vs `applyForce`: overriding motion vs. nudging it

*The `update()` hook* (5.2.21–5.2.22, appended 2026-11-02)
- `function update() { ... }`: optional, runs every frame before the physics step; `draw()` runs after it
- A velocity set in `update()` moves the sprite that same frame; set in `draw()`, it waits one frame
- Rules (keys, movement, the jump) in `update()`, picture (`background()`, text) in `draw()`

*Cleanup and win conditions*
- `sprite.delete()`: permanent, no undo, vs. `.visible = false` (temporary hide)
- Single-fire pattern: guard a repeatable condition so its side effect (a `console.log`, a state change) happens once

### Reading content guidance

#### R1: Gravity (`5-2-2-reading-gravity`)

- **Topic 1: `world.gravity.y` and dynamic vs static**: read before `5.2.8 Lab: Tune Gravity`.
  - **What you'll learn from it**: gravity is a per-world setting, not per-sprite; it starts at `0`, so nothing falls until a sketch sets it (moSHion's default since 2026-11-01, matching p5play); positive/zero/negative values; why `ground` is `static` and `player` isn't.
  - **Try it:** set `world.gravity.y` to `10`, `0`, `-5` in a live block with one dynamic sprite and log its `.y` each second; watch it fall, float, or drift up.
  - **Glossary rows:** `Gravity`, `dynamic`, `static`.

#### R2: Ground-Gated Actions (`5-2-4-reading-ground-check`)

- **Topic 1: `colliding()` and edge-triggered input**: read before `5.2.10 Lab: Add a Jump`.
  - **What you'll learn from it**: `sprite.colliding(other)` returns true while touching; `kb.presses` fires once per press where `kb.pressing` (§5.1) fires every frame held; why a jump needs both a press check and a ground check together.
  - **Try it:** live block that logs `"touching"` every frame `player.colliding(ground)` is true, then a second block that logs a message once per space-bar press using `kb.presses(' ')`.
  - **Glossary rows:** `colliding()`, `kb.presses` (edge-triggered).

#### R3: Bounciness and Friction (`5-2-6-reading-bounciness-friction`)

- **Topic 1: the two properties and the combining rule**: read before `5.2.12 Bouncy Ball`.
  - **What you'll learn from it**: bounciness (0–1) is retained speed after a collision; friction resists sliding; when two sprites' values disagree, bounciness takes the higher, friction takes a geometric mean.
  - **Try it:** set `.bounciness = 0.8` on a dropped sprite over a `static` floor and watch it rebound; then set it to `0` and compare.
  - **Glossary rows:** `Bounciness`, `Friction`.

#### R4: Forces vs Velocity (`5-2-8-reading-forces-vs-velocity`)

- **Topic 1: `applyForce` vs setting `.vel`**: read before `5.2.14 Lab: Wind Zone`.
  - **What you'll learn from it**: `applyForce(fx, fy)` is measured in Newtons, respects mass, and adds to existing motion; setting `.vel` directly (§5.1's idiom) overrides motion outright; when each is the right tool.
  - **Try it:** call `player.applyForce(0, -3)` every frame while a key is held, layered on top of gravity, and watch the sprite's fall slow rather than stop outright.
  - **Glossary rows:** `applyForce`.

#### R5: Cleanup and Delete (`5-2-10-reading-delete`)

- **Topic 1: `delete()` vs `.visible`**: read before `5.2.16 Worked Example: The Finished Scene`.
  - **What you'll learn from it**: `sprite.delete()` permanently removes a sprite (drawing, updating, and its physics body all gone, no undo); `.visible = false` only hides it, everything else keeps running.
  - **Try it:** delete a sprite on a key press and confirm a second press does nothing (it's really gone), versus toggling `.visible` and confirming the sprite comes back.
  - **Glossary rows:** `delete()`.

#### R6: update() runs before physics (`5-2-update-1-reading-update-runs-before-physics`)

- **Topic 1: the third hook**: read before `5.2.22 Lab: Rules in update(), picture in draw()`.
  - **What you'll learn from it**: moSHion runs `update()` every frame before the physics step and `draw()` after it; why the rules go in `update()` and the picture in `draw()`; `background()` stays in `draw()`; `kb.presses()` works in both; the name must be spelled exactly. Says plainly that one frame is too short to see, and that both ways work.
  - **Try it:** a console block that logs `update` then `draw` for frames 1–3, and the 5.2.10 jump scene split in two.
  - **Why here and not in 5.1:** owner decision 2026-11-02 (5.1 was already reviewed). Appended at the end of 5.2 so no number or `Help:` pointer moved. The starters in 5.3–5.16 keep their rules in `draw()`, and the reading tells students to build in the function a starter already uses.
  - **Glossary rows:** `update()`, physics step, `draw()`.

## Worked Examples (teacher-led)

### Worked Example 1: The Finished Scene (10 min)

Live-code (or walk through) the fully assembled player/ground/goal/walls scene from
book §5.2.6's solution: gravity, a ground-gated jump, bounciness/friction on player and
ground, a wind-zone force above y=200, and a single-fire "You win!" when the player
reaches the goal. This is the same scene A5.2.1 asks students to adapt into a pinball
layout — walking through the complete version first means the graded lab is a
modification, not a blank page.

```js
let player, ground, goal, leftWall, rightWall;

function setup() {
  new Canvas(400, 400);
  world.gravity.y = 10;
  player = new Sprite(200, 60, 40, 40);
  player.color = 'deepskyblue';
  player.bounciness = 0.2;

  ground = new Sprite(200, 380, 400, 20, 'static');
  ground.friction = 0.5;

  goal = new Sprite(360, 340, 24, 24);
  goal.collider = 'none';
  goal.color = 'gold';

  leftWall = new Sprite(6, 200, 12, 400, 'static');
  leftWall.color = 'sienna';
  rightWall = new Sprite(394, 200, 12, 400, 'static');
  rightWall.color = 'sienna';
}

function draw() {
  background('#222');
  if (kb.pressing('a'))       player.vel.x = -4;
  else if (kb.pressing('d'))  player.vel.x = 4;
  else                        player.vel.x = 0;

  if (kb.presses(' ') && player.colliding(ground)) {
    player.vel.y = -7;
  }

  if (player.y < 200) {
    player.applyForce(0, -3);
  }

  if (goal) {
    const dx = player.x - goal.x;
    const dy = player.y - goal.y;
    const dist = Math.sqrt(dx * dx + dy * dy);
    if (dist < 25) {
      console.log('You win!');
      goal.delete();
      goal = null;
    }
  }
}
```

## Vocabulary

| Term | Definition |
|---|---|
| Gravity | A force pulling dynamic sprites in a direction; `world.gravity.y` controls it |
| dynamic / static | A `dynamic` sprite is affected by gravity and forces (the default); a `static` one is immovable |
| colliding() | `sprite.colliding(other)` returns true while two sprites touch |
| kb.presses | Edge-triggered key check: fires once per press, unlike level-triggered `kb.pressing` |
| Bounciness | Restitution: how much speed a sprite keeps after a collision, `0`–`1` |
| Friction | Resistance to sliding along a surface; `0` is ice |
| applyForce | Pushes a sprite in Newtons, respecting mass, additive to existing motion |
| delete() | Permanently removes a sprite; no undo; contrast with `.visible = false` |

## Teacher Notes

- Beginners set `.bounciness = 1` and expect perpetual motion — that's lossless
  collision, not perpetual; friction still drains real systems. Worth a 30-second aside.
- The "why does `.vel` fight the physics engine" framing in A5.2.2 only lands if students
  actually tried both in the labs — don't skip 5.2.14 (Wind Zone) even if time is tight.
- Watch for students who set `player.vel.y = -7` unconditionally in `draw()` (no press
  check, no ground check) — it looks like "the sprite jumps" but is actually a
  60-times-a-second reset, and it's the most common way §5.2.6's Lab goes wrong.
- `.friction` and `.bounciness` interact with the *other* sprite in a collision (the
  combining rule). A student who sets bounciness only on `ground` and wonders why the
  ball doesn't bounce has the property on the wrong sprite — worth flagging before it
  becomes a 10-minute debug detour.
