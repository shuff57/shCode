# Module 3.9: Chapter 3 Group Performance Assessment

**Quarter 1 · Week 13 · Mon Nov 02, 2026 · One meeting · Paired · Environment: browser DevTools console**

The third Group PA of the year and the last one before the Print Shop. Same shape as
1.6 and 2.6 — one block, in pairs, three thirds: **design, build, demo**, with the
design third first and neither partner opening an editor until the plan is written
(3.9.1 is written pseudocode; Chapter 3 no longer teaches drawing flowcharts).

## Why this module is numbered 3.9

1.6/1.7 and 2.6/2.7 sit after their chapters' five book sections. **Chapter 3 has
eight** (§3.1–3.8), so its assessments are **3.9** (this) and **3.10** (the test).
Nothing else changes: the assessment modules are still "the two after the content",
which is what the numbering has always meant.

Two things keyed on the literal `.7` and had to be told:

- `scripts/check-summative-parts.mjs` matched test units with `/^(\d+)\.7 Chapter \1
  Individual Performance Assessment$/`. Against `3.10` that is simply false, so the
  check would have reported "ok" while examining none of 3.10's five parts — the exact
  failure it was written for. The section number is now `\d+`; the chapter
  backreference and the two literal words still keep teaching modules (3.7 Array
  Methods, 6.7 Advanced Input) and the Group PAs out.
- Sorting. `lib/curriculum.ts` orders modules and lessons with
  `localeCompare(…, { numeric: true })` and matches a lesson to its module with
  `numberedId.startsWith(moduleId + '.')`, so `3.10` sorts after `3.9` and does not
  collide with `3.1`. Both were already correct; neither had been exercised past `.9`.

## What 2.6 delivered and this one changes

2.6's program was one console script top to bottom with a loop in the middle, and its
own text said functions, arrays and objects were Chapter 3's. They arrive here. Three
things change and nothing else about the shape does:

| | 2.6 (Sep 28) | 3.9 (Nov 2) |
| --- | --- | --- |
| The program's shape | one straight script with a loop | **named functions** called from a short main section |
| The data | loose variables; iteration from a counter or `word[i]` | **an array of objects**, walked directly |
| What the design third produces | a drawn flowchart, with the loop-setup hexagon (§2.2) | **written pseudocode** that calls named functions (§3.1, §3.2) |

The named function call is the headline. In a drawn chart it was the double-rail; in the
written plan it is a line that calls `totalValue(stock)` and uses the answer. See
**How 3.9.1 is graded** below.

## What it assesses

All eight sections, once each, through one artifact:

| Section | Where it shows up |
| --- | --- |
| 3.1 Functions: Definition and Calls | The program is a set of named functions called from a short main section, not one long script |
| 3.2 Parameters and Return Values | Every function takes what it needs and **returns** a value; nothing does its work by printing (3.2.16) |
| 3.3 Arrays | The data is a list; a `for`/`for…of` loop walks it (3.3.5) and `push` builds a new one (3.3.2) |
| 3.4 Function Expressions and Arrow Functions | The callback handed to `.map()` is an arrow (3.4.12) |
| 3.5 Objects and Properties | Each record is an object literal read with dot notation (3.5.3) |
| 3.6 Functions: Pass by Value/Reference | One function is **required to mutate** what it was handed, and the demo has to say why the caller sees it (3.6.2) |
| 3.7 Array Methods | One transformation with `.map()`, one copy with spread (3.7.14) |
| 3.8 Saving and Loading Data | Save and load through `JSON.stringify`/`JSON.parse` under a key (3.8.15), with the failure case handled (3.8.12) |

## Timing for one 1.75-hour block

| Minutes | What |
| --- | --- |
| 0–8 | Pairs form, pick one problem from the menu of four, read the brief |
| 8–33 | **Design.** Contracts, then the pseudocode plan, written into 3.9.1. Editors for Part 2 stay closed. |
| 33–75 | **Build.** 3.9.2. One screen, partners swap the keyboard at least once. |
| 75–95 | **Demo — Gallery Walk.** Two waves (8 hosts / 7 visitors), ~3 min per station; teacher circulates with the rubric and samples 4–5 live. |
| 95–105 | Slack. |

Identical to 2.6's clock. The build is not bigger in minutes even though the program is
bigger in lines, and that is deliberate: the five functions are each three to six lines,
and what takes the time is deciding what goes in and what comes out — which is the
design third's job, not the build's.

**The design third gains a step 2.6 did not have: the contract table.** Before any
pseudocode is written, both partners write what each function *takes in* and *gives back*. It
is the §3.2 vocabulary made to do work, and it is the single best predictor of whether
the build goes anywhere. A pair that cannot say what `totalValue` returns will write a
function that prints — the 3.2.16 error, and the most common failure in this chapter.

## Why the plan is 25% and still comes first

Same reason as 1.6 and 2.6, one turn harder. In Chapter 2 the disagreement a pair had
to settle on paper was *what happens next* and *how many times*. Here it is **who owns
which step**: a plan that calls `totalValue(stock)` is a claim that some named function
does that job, and two students who have not agreed on the function list cannot write one.

A plan written after the code reads exactly like one and is graded as one.

## What this deliberately does not ask for

**No classes, no `this`, no constructors.** Those are §5.3 and §5.4. The program is
functions over plain objects.

**No `.filter()`, no `.reduce()`, no `.forEach()`, no `.sort()`.** This is the
constraint that shapes the whole build, and it is easy to get backwards. **§3.7 teaches
exactly four tools: `.map()`, `.slice()`, `.concat()` and spread.** 3.7.19 "What Else Is
Out There" *names* the others so students recognise them in someone else's code and says
in as many words that the book does not teach them. So:

- **Selecting a subset is hand-written**: an empty array, a loop, and `push` (3.3.2,
  3.3.5). The chapter's own worked example does exactly this — 3.3.17 "Keeping Only the
  Passing Scores" — and 3.3.19 makes a lab of it.
- **Totalling is hand-written**: an accumulator set before the loop and added to inside
  it (3.3.12 "Sum an Array").
- **`.map()` is the one that *is* taught**, so the one-line-per-record transformation is
  where a pair should reach for it rather than looping.

`curriculum-plan.md`'s Ch 3 Test blueprint says "`.map`/`.filter`/`.slice` on a supplied
array" and is **wrong about `.filter`** — the same plan-versus-shipped divergence 2.6
records for A2.2.0. `curriculum/modules/3.7_array-methods.md` states the shipped
position outright. Assess what shipped.

A pair that writes `.reduce()` anyway is not cheating — 3.7.19 told them it exists. See
the rubric: behaviour credit yes, technique credit no.

**No connector circles, no comment brackets.** Released at §4.1 (Appendix D §D.2).

## How 3.9.1 is graded

3.9.1 used to be a drawn flowchart with eleven legality checks. Chapter 3 no longer
teaches drawing flowcharts, so it is now a **written pseudocode part**, the same kind as
1.7.5 and 2.7.5: `preview: "assignment"`, a top-level `aiGrader` (summative, revisable,
three tries), no `diagram` block and no shape checker. There is nothing to be green
about; the AI feedback on the four rubric items is the whole check.

| Rubric item | What earns it |
| --- | --- |
| `functions-as-calls` | at least four of the five jobs written as named calls, handed what they need |
| `loop-over-the-list` | a loop whose indented body does something with each item |
| `change-one-record` | the mutating function called with the list and a name, and its effect reported afterwards |
| `save-and-load` | a load near the start and a save near the end |

Each item is met, partly met or missing, worth no points on its own; the part counts as
passed when at least half are met or partly met, and the manifest's max score is the item
count (4). Wording is not marked: any phrasing of the right idea counts, and the student's
text is data that cannot steer the grader.

**Part 2 reads the plan back.** 3.9.2 declares `planFrom` this lesson, shows the saved plan
read-only as "Your plan from 3.9.1", and seeds each pseudocode line as a `//` comment
under STEP 1 of the starter. A student who still holds an old drawn-chart draft sees the
chart as before. The seed is all `//` comments, which Part 2's grader strips before it runs the code checks
(`scripts/test-plan-seed.mjs` covers both plan kinds landing under STEP 1).

The reference answer is `pa-pseudocode/3-9-1-ch3-group-pa-design-chart.md` (git-ignored,
shown after the last try once released).

## The menu

Four problems, matched in difficulty and written to one template: **an array of record
objects with the same three fields (a name, a count and one more number); five functions
over it, each of the same kind — build one record, total the list (count times the other
number), select a subset (one comparison), one line per record, and lower one record's
count by one in place, never below zero — then save and load the list.** Full statements
are in 3.9.1.

1. **Snack Shack** — `{ name, price, qty }`. Total the inventory's value; list what is
   below a reorder level; one receipt line per item; sell one unit of a named item
   (mutates); save and reload the stock.
2. **Lap Times** — `{ name, laps, lapSeconds }`. Total the seconds run by the team; list
   the runners whose lap is above a target time; one result line per runner; take one
   lap off a named runner (mutates); save and reload the log.
3. **Seed Tray** — `{ variety, packets, seedsPerPacket }`. Total the seeds on hand; list
   the varieties below a packet level; one label line per variety; sow one packet of a
   named variety (mutates); save and reload the tray.
4. **Library Cart** — `{ title, copies, pages }`. Total the pages on the cart; list the
   titles longer than a limit; one spine line per title; check out one copy of a named
   title (mutates); save and reload the cart.

Pairs at adjacent tables should not pick the same one.

**Every one of the four has one function that must mutate and one that must not**, and
that pairing is the point rather than a detail. `sellItem` (or its equivalent) is handed
the list and has to change it where the caller can see — §3.6.2. The record-building
function has to hand back something new without touching its input — §3.7.14. A pair
that copies in the first and mutates in the second has written a program that runs and
is wrong in the way this chapter is about.

## The checklist's honest limits

Eleven token checks verify that Chapter 3's tools are **present**, never that the
program is right. The 2.6 loop measured this the hard way: an advanced student built a
15-line program that satisfied every check and solved nothing. The same is available
here — a `.map()` over a one-element array and a `push` into a list nobody reads would
go green.

The demo writeup is the defence. 3.9.3's Part 2 (three test cases, one landing on the
other side of the comparison) and Part 5 (name where each of the eight sections appears)
are where a paper program shows what it actually does. **Read those before you read the
code.**

One check is worth more than the others and cannot be gamed by accident: the §3.8 round
trip needs `JSON.stringify`, `JSON.parse` and `localStorage` all present. A pair that
saves without parsing back, or parses a key that was never written, fails the demo's
test-case part even when the checklist is green.

## Tries, feedback and the solution (from 2026-10-03)

Every part of this assessment gives each student **three tries**; the best one is the recorded score.
Partners are still graded separately, so each partner has their own three, even when they work
together. A banner at the top of every part says so before the first try and shows how many are left.

| Part | How a try is graded | After each try |
| --- | --- | --- |
| Plan | AI, against the four-item plan rubric | per-criterion feedback and a score |
| Build | the visible checklist (deterministic) | the checklist; Submit still needs it all green |
| Demo | AI, against the demo rubric | per-criterion feedback and a score |

**The build is the awkward one.** Its checklist is visible and Submit stays gated on every check
being green, so a student who gets there on the first submission has already got the best score
there is; the other two tries only matter if they edit and resubmit. It is capped for consistency, and
because the solution unlocks after the last try, a student who passed first time submits twice more
to see it. The alternative (reveal on any full-marks submission) was not taken, because the browser's
report is the only score the server has for a console part and would be a forgeable key to the solution.

**The solution.** After the last try the student sees the solution as plain-language pseudocode, once
the teacher releases it for the class (per part or per test, now or on a date, on the teacher page's
"Release solutions" panel). The text lives in `pa-pseudocode/<lessonId>.md`, which is git-ignored
because the repository is public (`pa-pseudocode/README.md`). Spec and record:
`.gauntlet/SPEC-attempt-caps.md`, `.gauntlet/attempt-caps-loop.json`.

## Teacher notes

- **Circulate during the design third, not the build third.** Unchanged from 1.6 and
  2.6, and still the note that matters most. What to listen for here is different: the
  question is no longer "where does your loop end" but **"what does that function give
  back?"** A pair who answer "it prints it" have the 3.2.16 error and thirty minutes to
  discover it the hard way.
- **A plan with no function names in it is the failure to look for.** The grader marks
  it down under `functions-as-calls`, but read the pseudocode yourself: a pair can write
  every job out inline and still have loops and a save. The plan is the pair's work, so
  both partners' submissions should show the same decomposition.
- **The one failure mode is still a silent partner.** The demo writeup asks who drove
  which third by name. Read that answer before you read the program.
- **A pair that finishes early has not finished.** Two questions, both cheap:
  - *"Call your save, then reload the page, then call your load. Does the list come
    back?"* Half the pairs will have written `setItem` and never read it (3.8.15).
  - *"What does your mutating function return, and what happens if I ignore it?"* The
    §3.6 answer is that the change already happened; a pair that has to think about it
    has found the chapter's real question on their own.
- **Hand this back as the study guide on Nov 2.** Every item type on the Ch 3 Test two
  days later has an analogue in the program the pair just built. Same policy as 1.6 → 1.7
  and 2.6 → 2.7, and it is not a secret. The test's menus use different problems.
- **Absent-partner policy:** the present member proceeds through all three thirds; the
  pair artifact and observed contribution are graded. The absent member completes an
  adjusted-scope solo make-up at a scheduled time; the present partner's grade is never
  affected by the make-up.
- **Odd-class trio policy:** one trio is permitted; roles (driver/navigator/recorder)
  rotate every 20 minutes; they produce one plan, one program, and the demo names all
  three and who drove which third. The 25/50/25 weights apply to the trio's single
  artifact.
