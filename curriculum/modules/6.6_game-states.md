# Module 6.6 — Game States

**Quarter 2 · ~3.5 contact hours**
**Environment:** moSHion in-app editor.

## SLO Focus
- **SLO 3** primary (structured programming via state machines)
- Reinforces **SLO 2** (one variable owns flow — composition over scattered booleans)

## Unit Goal
Students give their games a *shape*: title → play → game over → back. The unit introduces the state-machine pattern (`let gameState`, `switch (gameState)` in `draw`, input- and condition-driven transitions) and then integrates it with the save system from Unit 2.5 so a Continue actually restores the right screen. A16.2 ships a 4+ state machine with full save integration.

## Inter-module bridges
- **Unit 2.5 → 2.6.1:** A16.2 reuses the save system shipped in A16.1 — saves trigger on state transitions; Continue restores the right state.
- **Module 6.6 → next:** State machines are a structural prerequisite for any later capstone-style work; once a game has both a save layer and a state flow, it's a complete shippable artifact.

## Pre-requisite snapshot
- Module 2.5.1 complete — A16.1 save system is in hand and ready to be wired into state transitions.
- `if` / `else` familiarity from Q1 fundamentals (used as the contrast for `switch`).

## Post-requisite snapshot
- Can declare a state variable (`let gameState = 'title'`) and drive `draw()` with `switch (gameState)`.
- Can write input-driven transitions (`kb.presses(...) → gameState = '...'`) inside the right case.
- Can write condition-driven transitions (score / lives threshold → state change).
- Has implemented a 4+ state machine (title / play / pause / gameover / win).
- Can save on state transitions and load into the correct state on Continue.

## Unit-level assessments
None at unit close — A16.2 is the unit's graded artifact.
