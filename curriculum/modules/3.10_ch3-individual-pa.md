# Module 3.10: Chapter 3 Individual Performance Assessment

**Quarter 1 · Week 13 · Wed Nov 04, 2026 · One meeting · Individual · ~53 minutes**

The individual half of the chapter's assessment, and the sibling of the Group PA two
days before it: same chapter, same week, same in-app shape, sat alone. Five lessons,
17 items, 100 points — the identical skeleton to 1.7 and 2.7.

`curriculum-plan.md` calls this the heaviest test of Q1 and the last gate before the
Print Shop (§4.1, Fri Nov 6). Both are true, and they are the same fact: every line of
the Print Shop is functions over an array of objects.

## Why this module is numbered 3.10, and the check that did not know

Chapter 3 has eight book sections rather than five, so its Group PA is 3.9 and its test
is 3.10. That is the only structural difference from 1.7 and 2.7, and it broke one gate
silently:

**`scripts/check-summative-parts.mjs` keyed test units on `/^(\d+)\.7 Chapter \1
Individual Performance Assessment$/`.** `3.10 Chapter 3 Individual Performance
Assessment` does not match, so the check would have counted zero test units here,
printed `ok`, and examined none of these five parts. That is precisely the failure the
file exists to prevent — measured on 1.7 on 2026-09-03, where Parts 3 and 4 were
unflagged and a student stuck on Part 3's syntax error could not reach Parts 4 and 5 at
all and lost marks they had already earned.

Fixed: the section number is now `\d+`. The chapter backreference and the two literal
words still exclude teaching modules whose number ends in `.7` (3.7 Array Methods, 6.7
Advanced Input) and still exclude the Group PA units, which are deliberately not test
units. **Run `node scripts/check-summative-parts.mjs` before the day** and confirm it
reports three test units rather than two.

## The ceiling this test may not exceed

**No classes, no `this`, no constructors.** Those are §5.3 and §5.4. Every snippet is
plain functions over plain objects and arrays.

**No array method outside `.map()`, `.slice()`, `.concat()` and spread.** A Part B trace
that hands the student a `.reduce()` is asking them to read something 3.7.19 only named.
This cuts both ways and the generous direction matters: a student who *writes*
`.filter()` in D2 has done something 3.7.19 told them exists. Credit the behaviour, not
the technique — the rubric says how.

**Six shapes on D1, and the sixth is new.** Oval, rectangle, diamond, parallelogram, the
loop-setup hexagon (§2.2), and the **double-rail subroutine**, released at §3.1
(Appendix D §D.2). **Not released, must not appear:** the connector circle and the
comment bracket (§4.1).

**3.10.4 takes 3.9.1's rule block**, unchanged: `min-nodes: 10`, `min-process: 2`,
`min-decisions: 1`, and the other eight. 3.9's module doc sets out the survey and the
reasoning — the short version is that `min-process` counts rectangles only, and a
double-rail is no more a rectangle than a hexagon is, so the floor stays at 2 while
`min-nodes` carries the weight. Identical rules on both charts is also the fairer
arrangement when the PA is two days earlier and is handed back as the study guide.

**The printed syntax reference needs rebuilding for this chapter.** Ch 1's sheet was
declarations and the primitive types; Ch 2's was the loop forms, `switch` and
`try`/`catch`. Ch 3's is: the three function forms (declaration, expression, arrow) with
the shorthand rules, `return`, array literals with index and `.length`, `push`, object
literals with dot and bracket access, the four taught array methods, spread in an array
and in an object literal, `JSON.stringify`/`JSON.parse`, `localStorage.setItem`/
`getItem`, and the Appendix D shape table **including the double-rail**. Beginners are
assessed on whether they can reason, not on whether they memorised where the arrow's
braces change the meaning.

## Three forms, assigned automatically

Unchanged mechanism, restated so the module stands alone.

```
3.10.1 quiz ── variants: ["a","b","c"] ── hash(lessonId + student email)
                                              │
        ┌─────────────────────────────────────┼─────────────────────┐
        ▼                                     ▼                     ▼
   3 common concepts               3 common concepts       3 common concepts
   + 5 traces (form a)             + 5 traces (form b)     + 5 traces (form c)
        └──────── questions and options shuffled per student ───────┘
```

Eighteen questions authored; each student is asked eight. The five traces are the same
five *shapes* on every form — a function with no `return`, a callee mutating a passed
object, an index read against `.length`, an arrow's block body against its implicit
return, and a JSON round trip that drops something — with different names and values, so
the forms are genuinely equivalent. `lib/quiz-variant.ts` does the assignment;
`scripts/test-quiz.mjs` refuses to build a quiz whose forms come out different lengths.

**Vary the names and the values, never the trip.** 2.7 found the limit of that rule on
its nested-loop trace, where the bounds *are* the workload. Chapter 3 has a different
version of the same hazard: **the array length is the workload on t3 and t5.** Three
records to read is not four. So hold the record count constant across forms and vary the
field names and the numbers instead.

`scripts/test-quiz.mjs` refuses forms of different **length**. It cannot see any of
this; it is an authoring discipline and nothing more.

**The other four lessons are single-form, deliberately**, for the reason 1.7 gives:
Part C's answer is typed into a file rather than picked from a list, and D1/D2 offer a
menu of three problems from which the student picks one.

## `summative` hides the key on screen; two other pieces keep it off the wire

Inherited from 1.7 and 2.7 and still not automatic. `summative` governs what QuizView
and WrittenGrader *draw*; it does not govern what the page *ships*. `/lesson/[lessonId]/`
is statically exported with a client component body, so the whole `Lesson` object crosses
the boundary into the RSC payload.

| Piece | What it does | Where 3.10 depends on it |
| --- | --- | --- |
| `lib/quiz-redact.ts` → `redactLessonForClient()` | Strips `answer`, `explanation` and `source` from a summative quiz; strips `prompt` and `contextDocs` from a summative `aiGrader` | **Called in the SERVER page** (`app/lesson/[lessonId]/page.tsx`, `app/assignment/[id]/page.tsx`) — after the `'use client'` boundary it is already serialised and too late |
| `scripts/score-quiz.mjs <lessonId>` | Turns picks into marks on the machine that still has the key | 3.10.1 — with the key gone the browser **cannot** mark, so the submission records picks and a NULL score |
| `fetchSubmissions` (server) in `WrittenGrader.tsx` | Decides "already submitted" from the server, not localStorage | 3.10.2 and 3.10.5 — 30 of the 100 points |

### The Part C leak is still open, and 3.10.3 inherits it

**`redactLessonForClient()` covers `quiz` and `aiGrader`. It does not touch
`requirements`.** `LessonWorkspace` is a client component that reads
`lesson.requirements`, so every `Requirement` — **including `pattern`** — is serialised
into the page. On a Find-and-Fix part the patterns are the answer key.

This is live on 1.7.3 and 2.7.3 today and 3.10.3 is authored the same way, so it is not
a new defect — but it is worth knowing exactly what leaks here, because Chapter 3's
patterns are more explicit than Chapter 2's:

| Req | What View Source gives away |
| --- | --- |
| r1 | that the object literal needs a comma, and between which two properties |
| r2 | that the index has to come down by one, and the `length` form that does it |
| r3 | that the arrow's block body needs a `return` |
| r4 | that the copy has to be made with spread before the change |

`scripts/check-quiz-key-leak.mjs` collects only `quiz.summative` and
`aiGrader.summative`, so it is structurally blind to this;
`check-summative-parts.mjs` only asserts the flag is set. The fix is the same shape as
the quiz fix — strip `pattern` from a `grading.summative` lesson's requirements before
the client boundary, keep `title`/`description`/`hint`, and teach
`check-quiz-key-leak.mjs` to scan the built page for each pattern. Until then, the
practical mitigation is the one Part C already relies on: **the `hint` names the symptom,
never the repair**, and the teacher marks from the submission rather than the checklist.

Two consequences to plan for rather than discover:

- **Part A's marks do not exist until you run `score-quiz.mjs`.** Budget that; it sits
  between the period ending and a number going into Aeries.
- **`stripKey()` is a rebuild, not a delete.** It names the fields it keeps — `id`,
  `question`, `options`, `code`, `variant` — so a question that grows a new key-bearing
  field must be added there on purpose. 3.10.1's traces use `code`, which is kept.

and `passingScore` is 0, as everywhere else in the course. The teacher reads the
submissions from the teacher view and enters one score per student in Aeries.

Homework/Classwork 35%, Group Assessments 15%, Individual Assessments 50%. Chapter tests
go under **Individual Assessments (50%)**. (`curriculum-plan.md`'s GRADING STRUCTURE
