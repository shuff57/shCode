# Module 1.6: Chapter 1 Group Performance Assessment

**Quarter 1 · Week 4 · One meeting · Paired · Environment: browser DevTools console**

This is the chapter's performance assessment, and it is the first one of the year.
It runs in a single block, in pairs, in three thirds: **design, build, demo.** The
design third is a flowchart and it comes first — neither partner opens an editor
until the chart is green (Appendix D).

## What it assesses

Everything in Chapter 1 at once, which is the point. No section is assessed twice
and none is left out:

| Section | Where it shows up |
| --- | --- |
| 1.1 Software Lifecycle | The demo names which lifecycle phase each third of the period was |
| 1.2 Variables and Data Types | Three distinct primitive types in the program, reported with `typeof` |
| 1.3 Documentation and Conventions | Header comment, pseudocode comments, inline comments, camelCase names |
| 1.4 Paradigms and Languages | The demo names the paradigm the program is written in, and why |
| 1.5 Program Design Tools | The flowchart, the pseudocode, the test-case table, the `console.log` trace |

## Weights

| Third | Weight | Lesson |
| --- | ---: | --- |
| **Design** — the flowchart, drawn together, all checks green | 25% | 1.6.1 |
| **Build** — the program, documented to the style guide | 50% | 1.6.2 |
| **Demo** — run it, test it, explain it | 25% | 1.6.3 |

The in-app lessons are green-to-advance like every other lesson in the course.
The 25/50/25 split is how the three artifacts are weighted in the gradebook, not
something the checker computes.

## Timing for one 1.75-hour block

| Minutes | What |
| --- | --- |
| 0–10 | Pairs form, pick one problem from the menu of four, read the brief |
| 10–35 | **Design.** Pseudocode on paper, then the chart in 1.6.1. Editors stay closed. |
| 35–75 | **Build.** 1.6.2. One screen, partners swap the keyboard at least once. |
| 75–95 | **Demo.** 1.6.3 writeup, then run the program for the teacher. |
| 95–105 | Slack. Some pair will spend 20 minutes arguing about the chart, which is the pairing working. |

## Why the flowchart is 25% and comes first

Two students who disagree about what happens next have to settle it on the diagram
before either of them can type. That argument is the assessment. A pair that skips
it produces a chart drawn after the code, which reads exactly like one and is
graded as one (Appendix D §D.7).

## What this deliberately does not ask for

**No `if` statement.** Conditionals are Chapter 2. The chart has a diamond because
1.5 teaches the diamond, and the program answers that diamond by *computing a
boolean* with a comparison — which 1.2 does teach — and printing it. The two
branches are written out as pseudocode comments. Chapter 2's Group PA is where they
become code.

**No functions, no loops, no arrays.** The program is a straight line. That is not a
simplification, it is the honest ceiling of what Chapter 1 taught, and it is the same
reason the Chapter 1 Test's Part D is a chart and pseudocode rather than JavaScript.

## The menu

Four problems, matched in difficulty, all the same shape: take some numbers in,
compute one value, compare that value against a fixed threshold. Full statements
are in 1.6.1.

1. **Slice Economics** — cost per slice of a pizza, against a good-deal limit
2. **Split the Check** — cost per person after tip, against what everyone agreed to
3. **Grade Forecast** — a weighted course average, against the passing mark
4. **Fuel Stop** — how far a tank goes, against the length of the trip

Pairs at adjacent tables should not pick the same one.

## Teacher notes

- **Circulate during the design third, not the build third.** The build is where it
  looks like the work is happening and the design is where the work actually is.
  A pair whose chart is green in four minutes has drawn a straight line with no
  diamond; send them back.
- **The one failure mode is a silent partner.** The demo writeup asks who drove
  which third by name. Read that answer before you read the program.
- **A pair that finishes early has not finished.** Ask them for a fourth test case
  that breaks their program. Every one of these four problems has one — a zero, a
  negative, a string where a number belongs.
