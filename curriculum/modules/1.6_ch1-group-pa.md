# Module 1.6: Chapter 1 Group Performance Assessment

**Quarter 1 · Week 4 · One meeting · Paired · Environment: browser DevTools console**

This is the chapter's performance assessment, and it is the first one of the year.
It runs in a single block, in pairs, in three thirds: **plan, build, demo.** The
plan third is a pseudocode plan the pair types, and it comes first — neither partner
opens the build editor until the plan is submitted. The plan is the Chapter 1
pseudocode of 1.5.19 and 1.5.20 (`START`, `INPUT`, `SET ... TO`, `IF ... THEN`,
`ELSE`, `END IF`, `PRINT`, `END`; one instruction per line, indent what is inside).

## What it assesses

Everything in Chapter 1 at once, which is the point. No section is assessed twice
and none is left out:

| Section | Where it shows up |
| --- | --- |
| 1.1 Software Lifecycle | The demo names which lifecycle phase each third of the period was |
| 1.2 Variables and Data Types | Three distinct primitive types in the program, reported with `typeof` |
| 1.3 Documentation and Conventions | Header comment, pseudocode comments, inline comments, camelCase names |
| 1.4 Paradigms and Languages | The demo names the paradigm the program is written in, and why |
| 1.5 Program Design Tools | The pseudocode plan, the test-case table, the `console.log` trace |

## Weights

| Third | Weight | Lesson |
| --- | ---: | --- |
| **Plan** — the pseudocode plan, written together and AI-marked against the chosen problem | 25% | 1.6.1 |
| **Build** — the program, documented to the style guide | 50% | 1.6.2 |
| **Demo** — run it, test it, explain it | 25% | 1.6.3 |

The in-app lessons are green-to-advance like every other lesson in the course.
The 25/50/25 split is how the three artifacts are weighted in the gradebook, not
something the checker computes.

## Timing for one 1.75-hour block

| Minutes | What |
| --- | --- |
| 0–10 | Pairs form, pick one problem from the menu of four, read the brief |
| 10–35 | **Plan.** The pseudocode plan, typed together in 1.6.1. The build editor stays closed. |
| 35–75 | **Build.** 1.6.2. One screen, partners swap the keyboard at least once. |
| 75–95 | **Demo.** 1.6.3 writeup, then run the program for the teacher. |
| 95–105 | Slack. Some pair will spend 20 minutes arguing about the plan, which is the pairing working. |

## Why the plan is 25% and comes first

Two students who disagree about what happens next have to settle it in the plan
before either of them can type code. That argument is the assessment. A pair that skips
it produces a plan written after the code, which reads exactly like one and is
graded as one (Appendix D §D.7). 1.6.2 opens the saved plan beside the code (`planFrom`).

## What this deliberately does not ask for

**No `if` statement in the code.** Conditionals are Chapter 2. The plan has an `IF`
because 1.5 teaches it in pseudocode, and the program answers that `IF` by *computing a
boolean* with a comparison — which 1.2 does teach — and printing it. The two
branches are written out as pseudocode comments. Chapter 2's Group PA is where they
become code.

**No functions, no loops, no arrays.** The program is a straight line. That is not a
simplification, it is the honest ceiling of what Chapter 1 taught, and it is the same
reason the Chapter 1 Test's Part D is two typed pseudocode plans rather than JavaScript.

## The menu

Four problems, matched in difficulty, all the same shape: take some numbers in,
compute one value, compare that value against a fixed threshold. Full statements
are in 1.6.1. The plan is typed into the lesson's `README.md` (a `Problem:` line, a
`Partners:` line, then the plan); a read-only "Flow Chart" bar shows a worked plan for a
bus pass, which is not one of the four.

1. **Slice Economics** — cost per slice of a pizza, against a good-deal limit
2. **Split the Check** — cost per person after tip, against what everyone agreed to
3. **Grade Forecast** — a weighted course average, against the passing mark
4. **Fuel Stop** — how far a tank goes, against the length of the trip

Pairs at adjacent tables should not pick the same one.

## Tries, feedback and the solution (from 2026-10-03)

Every part of this assessment gives each student **three tries**; the best one is the recorded score.
Partners are still graded separately, so each partner has their own three, even when they work
together. A banner at the top of every part says so before the first try and shows how many are left.

| Part | How a try is graded | After each try |
| --- | --- | --- |
| Plan (1.6.1) | typed pseudocode; the AI marks three criteria against the chosen problem (inputs and the value's arithmetic, the comparison against the problem's own limit, a different report on each side). The regex requirement cards are only a fallback when the AI is down | per-criterion feedback and a pass or not yet |
| Build | the AI reads the code against eight one-point criteria (`aiGrader`, summative, revisable, strict; passed at 70%); **Grade (N left)** counts a try. The regex cards beside it are the fallback if the AI is down, and still carry the same ids | per-criterion feedback and a score out of 8; moving on happens after any counted try |
| Demo | AI, against the demo rubric | per-criterion feedback and a score |

**The build is the awkward one.** Its checklist is visible and Submit stays gated on every check
being green, so a student who gets there on the first submission has already got the best score
there is; the other two tries only matter if they edit and resubmit. It is capped for consistency, and
because the solution unlocks after the last try, a student who passed first time submits twice more
to see it. The alternative (reveal on any full-marks submission) was not taken, because the browser's
report is the only score the server has for a console part and would be a forgeable key to the solution.

**The solution.** After the last try the student sees the solution as plain-language pseudocode, once
the teacher releases it for the class (per part or per test, now or on a date, on the teacher page's
"Release solutions" panel). The text lives in `pa-pseudocode/<lessonId>.md`, which is git-ignored
because the repository is public (`pa-pseudocode/README.md`). Spec and record:
`.gauntlet/SPEC-attempt-caps.md`, `.gauntlet/attempt-caps-loop.json`.

## Teacher notes

- **Circulate during the design third, not the build third.** The build is where it
  looks like the work is happening and the design is where the work actually is.
  A pair whose plan is done in four minutes has typed a straight line with no
  `IF`; send them back.
- **The one failure mode is a silent partner.** The demo writeup asks who drove
  which third by name. Read that answer before you read the program.
- **A pair that finishes early has not finished.** Ask them for a fourth test case
  that breaks their program. Every one of these four problems has one — a zero, a
  negative, a string where a number belongs.

## Grading note: r3 accepts two spellings on purpose

The course dropped `UPPER_SNAKE_CASE` on 2026-09-19. One naming rule now covers
every value — camelCase — and `const` alone carries *this never moves*; 1.3.2
teaches it that way and `class-style-guide.md` records it.

This module ran in **week 4, under the old rule**, so `1.6.2`'s r3 pattern reads
`const\s+(?:[a-z][A-Za-z0-9]*\s*=\s*\d|[A-Z][A-Z0-9_]{2,}\s*=)`. The second
branch is the week-4 pattern **verbatim**, so a paper already handed in scores
exactly what it scored then; the first carries the current rule. Verified through
`lib/grader.ts`: both spellings score 10/10.

**Do not collapse the alternation.** It is a grandfather for submitted work, not
redundancy. Modules 2.6 and 3.9 are deliberately *not* grandfathered — they open
Sep 28 and later, have no submissions behind them, and their r3 rejects the old
spelling so the single convention is what students meet.
