# Part Objects

Students transfer familiar classes and instances from moSHion into CAD. One object
keeps one part's measurements; its `build()` method appends that part's feature recipe.
The outcome is two independently described solids, with an explanation of why changing
one object need not change the other.

This is a proposed build spec outside the live module loader. Its numbers are candidate
slots, not created lesson ids. Concept sources are the existing object modules 7.1–7.3,
book §9.2's primitives/placement, and the measured 9.1.12 pilot. The final book-to-module
join must be recorded when the spec is approved; do not rename book sections.

## Outcomes and prerequisites

Students can distinguish a part description from its built solid, store measurements
with `this`, use a method to build one part, create two independent instances, and
predict the result of changing one property before rebuilding.

Prerequisites: JavaScript classes, `new`, constructors, methods and properties from
7.1–7.3; reading/writing a short box recipe, coordinates, millimetres and Run from 9.1.
A student who cannot explain `this` needs the prior OOP practice, not a second CAD API.

Atomic CAD ideas: a part description; constructor stores measurements; method emits a
recipe; placement belongs to the instance; independent instance state; build time vs
later property changes. The syntax is review, but its CAD meaning is practiced in
separate screens.

## Lesson authoring briefs

**9.2.1–2:** show an object with one width and a method that reads it. The contrast is
object state vs model output, not class vs every other programming paradigm. Ask the
prediction before showing a run. Avoid the phrase “the object on the screen” for both.

**9.2.3:** starter supplies the class shell and correct build method. The student writes
only constructor storage. Accept another sensible class/argument name. An empty class,
a commented-out assignment and a hard-coded matching width cannot be the full reference.

**9.2.4–6:** add x as one new instance property. Do not combine this with rotation,
centering conventions and hole placement. Build reference widths 28 and 44, positions 0
and 80, depth 20 and height 6. The widths differ from the pilot so it is not a copy task.

**9.2.7–8:** put aliasing in a prediction before asking students to debug it. Two
variables assigned to the same object are not evidence of two independent instances.
The lab changes the first width before either build call and verifies the second stays
unchanged. Use ordinary property assignment rather than introducing a setter method.

**9.2.9:** ship the wrong global-width lookup in an otherwise correct short program.
Check two input configurations. A visually correct first case does not prove instance
state is used. Keep this as one bug, not a collection of syntax errors.

**9.2.10:** distinguish a program run from a method call during that run. In each Run,
build once, change the object, then reason about the already-emitted recipe. A second
Run starts the script again; it does not retain an arbitrary in-memory JavaScript object
from the previous run. Do not teach duplicate build calls as a resizing mechanism.

**9.2.11–12:** the integration asks for one reusable class, two instances and a single
intentional variation. The exit problem changes the names and values. Neither requires
inheritance, a returned body handle, arrays, holes or manual modelling tools.

## Worked example for the teacher

```js
class Spacer {
  constructor(width, x) {
    this.width = width;
    this.x = x;
  }

  build() {
    box(this.width, 20, 6, { at: [this.x, 0, 0] });
  }
}

const left = new Spacer(28, 0);
const right = new Spacer(44, 80);
left.width = 32;
left.build();
right.build();
```

Before Run: predict two parts, widths 32 and 44. Afterward, trace each visible width
back to an instance property. This is an authoring reference, not the lab starter.

## Assessment and wrong answers

Use the current model/refusal report for shape criteria, and source criteria for the
class task. Accept aliases and harmless formatting. Readable source plus the requested
solid is necessary, but a source pattern alone cannot prove independence; the changed
configuration and explanation supply the additional evidence.

| Attempt | Expected handling |
| --- | --- |
| Unfinished constructor | Does not satisfy the instance-storage task |
| Both parts use one global width | Second configuration reveals the mistake |
| Two names alias one object | Prediction/debug response identifies shared state |
| Correct text but no current Run | Geometry criterion and Submit remain unavailable |
| Hand-made matching boxes | Do not count as a completed script/class lab |
| One box refused | The refused feature is not graded as built; its sentence stays visible |

Mastery is criteria met, not accumulated points. Retain the source, changed-input
observation and exit response as SLO 2/3 evidence. Use the 9.1.12 pilot as optional
bridge/review material without moving it into a second module or changing its id.
