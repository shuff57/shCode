# Measurements and Part Families

Students turn a part class into a small family of related designs. They identify
which numbers come from a real object, which are design choices, and which must be
derived. A classmate should be able to change the documented inputs without rewriting
the build method.

Candidate slots only; this file is not a live module. Concept sources: book §8.4's
parametric intent, §9.2 dimensions, earlier JavaScript function/object work, and the
old parametric-box/washer/swap activities. JSCAD's panel API is not assigned as if it
worked in reSHape. The initial interaction is editing a named input block and Run.

## Outcomes and prerequisites

Given a measured bolt and a stated diametral clearance, students derive a hole's
across size, explain the relationship and check another input. They can keep one set
of configuration values together, distinguish stored and derived values, and document
what a classmate may change.

Prerequisites: 9.2 part objects and build timing; JavaScript arguments, arithmetic,
plain objects, property access and pure functions. Plain box/hole recipes are already
familiar. This module does not introduce GUI sliders, sketch constraints, loops or
manufacturing tolerances as universally correct constants.

Atomic ideas: measured input; design allowance; derived dimension; a configuration
record; recomputing a derived value; explicit input validation; a documented input
contract; transfer to a second configuration. These get separate encounters below.

## Lesson authoring briefs

**9.3.1–3:** the supplied part is a rectangular blank. If object width is `w` and the
chosen border is `b` on each side, its outside width is `w + 2*b`. Call it a blank,
not a finished holder: no cavity has been cut. The lab changes `w` and checks whether
the model follows; a copied outside-width literal is not full evidence.

**9.3.4–5:** a bolt measured 6 mm across with 0.2 mm **diametral** clearance asks for a
6.2 mm bore. A 0.2 mm **radial** clearance asks for 6.4 mm across. These are arithmetic
examples, not a recommendation for the classroom printer. A real clearance is tested
later with a coupon. Keep the labels visible in every task.

**9.3.6–8:** plain-object syntax is review. A configuration record states the external
inputs; the instance stores the values it needs. Supply a complete build method while
students refactor only the input boundary. The closing trace must name the unit and
the feature the derived value controls.

**9.3.9–10:** present a constructor that stores `this.holeAcross` once. Changing
`this.boltAcross` later cannot recompute that old number. Fix the causal relationship
by calculating the bore during `build()` or calling a pure helper then. Do not teach
special live setters or automatic dependency propagation that the interpreter lacks.

**9.3.11–13:** use a plain helper with an explicit input contract, tested in shCode's
existing console runner. Empty, zero, negative, nonnumeric and large values are distinct
cases; pick a small justified set for this introductory task. The CAD integration
reuses the tested helper. A source exception prevents that run from reaching the engine;
a kernel feature refusal happens later and uses the host's sentence, not the helper's
`catch` block. Full test-design instruction comes in chapter 12.

**9.3.14–16:** the product is a gauge/fit coupon: a flat plate and a central plain
through bore. Supply fixed outer dimensions and vary only the documented inputs.
Partners may edit a few input values; they do not have to understand or alter the
method body. Capture the digital result and the input contract, not a fabricated
“fits my bolt” claim before the coupon has been made.

## Teacher worked example

```js
class FitCoupon {
  constructor(config) {
    this.boltAcross = config.boltAcross;
    this.diametralClearance = config.diametralClearance;
    this.x = config.x;
  }

  build() {
    const holeAcross = this.boltAcross + this.diametralClearance;
    const body = box(36, 24, 6, { at: [this.x, 0, 0] });
    hole(body, { across: holeAcross });
  }
}

const first = new FitCoupon({ boltAcross: 6, diametralClearance: 0.2, x: 0 });
const second = new FitCoupon({ boltAcross: 8, diametralClearance: 0.4, x: 60 });
first.build();
second.build();
```

Ask for the two across sizes before Run. These input records are the proposed handoff
interface. They do not create sliders, trigger a live property update or certify a
physical fit.

## Assessment and expected failures

References must succeed under at least two configurations; the untouched starter must
not pass all criteria. Shape checks exclude refused features and require a current Run.
Accept equivalent arithmetic and sensible names. Supplement source patterns with the
changed-input task so a hard-coded duplicate cannot masquerade as parametric behaviour.

| Attempt | Evidence or handling |
| --- | --- |
| Adds the diametral allowance twice | Arithmetic prediction and bore check reveal the extra allowance |
| Keeps a derived bore fixed after a property change | Changed-input case reveals stale state |
| Renames fields consistently | Accept if the documented input contract and output remain correct |
| Invalid input produces a source error | Explain the input issue; do not count old geometry as the new result |
| A feature is refused after evaluation | Show its host sentence; it cannot satisfy the model criterion |
| Matching model built by hand | Not evidence of a reusable input-driven program |

Artifacts: source/configuration, a labelled dependency trace, helper test inputs/results,
and peer handoff notes. Mastery is criteria met. Preserve SLO 2/3 evidence; do not add a
second grading scale in the spec.
