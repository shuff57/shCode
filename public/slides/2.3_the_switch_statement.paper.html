One Value, Many Answers

In Section 2.1 you chained conditions with else if. That chain works for any conditions, which is why it is the tool you reach for first.

§2.3.2 — The value, written once

The switch Statement

A switch takes one value and compares it, in order, against a list of case values. When it finds a match, it runs the code for that case.

switch (day) {
  case 1:
    console.log("Monday");
    break;
  case 2:
    console.log("Tuesday");
    break;
  // ... cases 3, 4 and 5 look the same ...
  default:
    console.log("Weekend");
}

§2.3.2 — Read it the way JavaScript does

Top to bottom, first match wins

  1. switch (day) — the value being tested, written once.
  2. case 1: — is day equal to 1? No. Move on.
  3. case 2: — no. Move on.
  4. case 3: — yes. Run the code that follows.
  5. break; — stop here and leave the switch.

The default: clause is the else of a switch: it runs when no case matched. It is optional, and by convention it goes last.

Insight Note — why the ladder is fragile

The repetition is a symptom

The repetition is not the problem by itself — it is a symptom. Six copies of day === means six chances to typo the variable name, and a typo like if (dat === 4) does not crash. It simply never matches, and Thursday quietly disappears from your program. A switch names the value once, so that class of bug cannot happen.

§2.3.2 — The central idea

Definition 2.3.1: switch Statement

Definition 2.3.1 — switch Statement

A switch statement compares a single value against a list of case values in order and runs the code belonging to the first case that matches. An optional default clause runs when no case matches.

switch (value) {
  case a:  /* runs if value === a */  break;
  case b:  /* runs if value === b */  break;
  default: /* runs if nothing matched */
}

Definition 2.3.1: switch Statement.

One value, tested once, against the cases in order. default is the else; break is the exit.

§2.3.3 — break is not decoration

Remove every break

Without it, JavaScript does something surprising: once a case matches, execution keeps going through the cases below it — running their code too, without checking any of their values.

const selection = "A";

switch (selection) {
  case "A":
    console.log("Dispensing: chips");
  case "B":
    console.log("Dispensing: pretzels");
  case "C":
    console.log("Dispensing: cookies");
  default:
    console.log("Unknown selection. Refunding your money.");
}

Context Pause — reading the tell

A bug that does not crash

Notice that the broken version did not crash, and did not warn you. It ran, printed four lines, and looked like it worked. A missing break is a logic bug, and the tell is always the same — you see output from cases you did not expect. When a switch prints too much, look for the missing break above the surprising line, not at the surprising line itself.

Definition 2.3.2 — Fall-Through

Fall-through is what happens when a matched case has no break: execution continues into the following cases and runs their code without testing their values.

Definition 2.3.2: Fall-Through.

A feature when the labels are stacked on purpose; a bug when a break went missing. Same mechanism, and only the reader can tell which.

§2.3.4 — Fall-through on purpose

Grouping Cases

When several values should produce the same result, stack their case labels with no code between them and let the first ones fall into the last.

switch (day) {
  case "Saturday":
  case "Sunday":
    console.log("It is the weekend.");
    break;
  default:
    console.log("It is a weekday.");
}
if (day === "Saturday" ||
    day === "Sunday") {
  console.log("It is the weekend.");
} else {
  console.log("It is a weekday.");
}

Both are correct. Grouped cases are the switch spelling of ||.

Insight Note — grouping vs. a missing break

Intent, or oversight?

Deliberate grouping and an accidental missing break are the same mechanism. The difference a reader can see is whether there is any code between the stacked labels. case "Saturday": immediately followed by case "Sunday": reads as intent; a case with three lines of code and no break reads as an oversight. If you ever want to fall through after running code, say so in a comment — the next person to read it will assume you forgot.

§2.3.5 — Same-looking is not the same

switch Compares Strictly

A case matches using ===. The value and the case must be the same type, not just the same-looking content — and values that arrive from outside your program are almost always strings.

const answer = "3";        // from a form field: a STRING

switch (answer) {
  case 3:                  // a NUMBER
    console.log("You chose three.");
    break;
  default:
    console.log("Not a valid choice.");
}

Prints Not a valid choice. — "3" is not strictly equal to 3, so case 3 never matches. It is dead code, sitting in your program looking perfectly reasonable.

§2.3.5 — Two fixes

Which fix depends on what the value really is

Fix 1 — the value is a string, so the cases are strings

switch (answer) {
  case "1": /* ... */ break;
  case "2": /* ... */ break;
  case "3":
    console.log("You chose three.");
    break;
}

Fix 2 — convert the value to a number first

switch (Number(answer)) {
  case 1: /* ... */ break;
  case 2: /* ... */ break;
  case 3:
    console.log("Converted: three.");
    break;
}

Either way the burden is on you to know what type your value actually is. switch will never guess.

Context Pause — no == in a switch

Always strict, on purpose

Recall from Section 2.1.2 that == would have matched "3" against 3, because it converts types before comparing. switch gives you no such option — it is always strict. That is a feature, not a limitation: it means a switch never matches something you did not intend. But it does put the burden on you to know what type your value actually is.

§2.3.6 — Neither is better

Choosing Between if...else and switch

They fit different shapes of problem.

Reach for switch

One value compared against a list of specific values: "north", "south", a menu letter, a day number. It names the value once and gets shorter as the list grows.

Reach for if...else

Ranges (score >= 90), more than one variable, && or ||, or anything other than a plain equality test.

The grade chain cannot become a switch: score >= 80 is not a value you can list as a case. There is no fixed set of numbers to match — there is a boundary.

Insight Note — the question that decides

Can you list the values?

The question to ask is not "which one is cleaner". It is: can I write the whole test as a finite list of exact values? If yes, switch says that intent out loud and gets shorter as the list grows. If no — ranges, two variables, &&, || — it is an if...else chain, and forcing a switch onto it produces something worse than what you started with.

Glossary — terms introduced in this section

Key Terms

switch statement

A statement that compares one value against a list of case values in order and runs the code for the first match.

case

A labelled branch inside a switch giving one value to compare against and the code to run on a match.

default

The optional clause in a switch that runs when no case matched; the switch equivalent of else.

break

The statement that ends a switch immediately, preventing execution from continuing into the cases below.

Fall-through

Execution continuing from a matched case into the following cases because no break stopped it. A bug when accidental, a technique when cases are deliberately grouped.

Grouped cases

Several case labels stacked with no code between them so they all run the same block.

Strict equality (===)

Comparison that requires the same type as well as the same value; the comparison a switch always uses.

Dead code

A line or branch that can never run, such as case 3: when the switched value is always a string.

§2.3 — Conclusions

What to carry forward

The one idea

A switch compares one value, strictly, against a list of case values in order and runs the first match. break leaves the block, default catches everything else, and stacked labels share one body — the switch spelling of ||.

The common mistake

A missing break. Execution falls through into the cases below and the program prints too much without crashing or warning. Close behind it: a case 3: that can never match a "3" from a form, because switch never converts types.
